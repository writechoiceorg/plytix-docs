# Documentation Outline: Plytix API Documentation

Plytix is a Product Information Management (PIM) / content-led-growth platform. This outline covers the developer-facing documentation for Plytix's API — primarily v3, with v1/v2 kept accessible for the workflows v3 doesn't yet cover — aimed at the technical internal users, integration engineers, and partner developers who connect their own systems (ERPs, storefronts, internal tools) to a Plytix account, plus the emerging AI-agent audience using it through Plytix's forthcoming MCP server. It is deliberately separate from the existing Plytix Help Center, which covers the dashboard/UI for non-technical end users.

---

## Tab: Guides

Learning- and task-oriented content: onboarding, the concepts an integration needs before it touches the API reference, and step-by-step guides for the real integration jobs Plytix's own stakeholders and customer data say developers actually do.

### Getting Started

Gets a new developer from zero to a working, authenticated connection, and orients them to the two-API reality (v1/v2 and v3) before they write any integration code.

* **Overview** [`Concept`]: What the Plytix API is for, who it's for (technical internal users, integration engineers, partner developers, and AI agents/IDEs via the coming MCP server), and how this documentation relates to the separate Help Center. Already drafted at `docs/guides/overview.mdx` — content holds up, no corrections needed.
* **Get Started with the API** [`Tutorial`]: Generate an API key, exchange it for a bearer token, and make a first authenticated `GET /products` call, ending in a real response. Already drafted at `docs/guides/get-started-with-api.mdx` and matches the confirmed-live flow exactly (token lifetime, header format, response shape) — no corrections needed, though its sample response's `pagination` block should show `next_page`/`previous_page` as the only confirmed fields (no `filtered_count`/`total_count` were observed live).
* **The Plytix Data Model** [`Concept`]: How Products, Attributes (keyed by `name`, not `id`, on a product's `attributes` map), Categories, Assets, and Relationships fit together, including the real field name (`product_relationships`, not the spec's `relationships`) and the read-only nature of Product Families/Product Family Models/Relationships.
* **Choosing v1/v2 or v3** [`Concept`]: Explains today's split — v3 is the modern, actively-developed API (better filtering, automatic asset/category expansion, no 50-attribute limit) but Plytix's own product team states that product create/update/delete workflows should still go through v1/v2 today. **Flagged as needing Plytix confirmation before publishing**: live testing this engagement ran directly against v3 (`POST`/`PATCH`/`DELETE /products`) and confirmed all three work end-to-end on a real (non-production) account — so it's unclear whether v3 writes are technically live-but-not-yet-GA'd for customers, or whether the product team's guidance is already stale. Don't resolve this either way without asking Plytix; present both facts and the open question.

### Core Concepts

The request/response mechanics and structural realities every integration needs, several of which only became knowable through live testing — the raw materials alone would have led a reader astray on more than one of these.

* **Filtering, Sorting & Pagination** [`Concept`]: The conceptual introduction to querying product/asset data — what a filter, sort, and page of results look like conceptually, before the exhaustive syntax reference. Frames `in`, `eq`, `exists`/`!exists`, and `like` as the everyday operators (74% of all real filter usage per Plytix's own usage analysis) and the new `_or[index]` OR-logic as the single highest-value v3 improvement to lead with (replaces a common workaround pattern of repeated near-identical filters).
* **Response & Error Conventions** [`Concept`]: The `data`/`errors`/`pagination` envelope shape, and — critically — that error responses are **not** one consistent shape: a nested nested `error.msg` shape on the auth endpoint's 401, a flat `errors: [{name, description}]` array on most 4xx/5xx responses elsewhere, and no confirmed live sighting of the FastAPI-default `HTTPValidationError`/`detail` shape the current draft reference page describes.
* **Working with Relationships, Categories & Assets on a Product** [`Concept`]: How `_fields` automatically expands related data (no working `_expand` mechanism exists on `/products` despite `API V3.md` describing one), the subpath-discovery trick (`GET /{resource}/{id}/{bad-path}` lists real internal field names), and a prominent warning that `DELETE /products/{id}/{path}` deletes the **entire product** regardless of `{path}` — full detail and safe alternatives live in the dedicated how-to guide below.
* **Updating and Deleting Resources Beyond Products & Assets** [`Concept`]: `openapi_pimv3.json` declares `PATCH`/`DELETE` on only 2 of the roughly 15 writable v3 resources — yet live testing confirmed undeclared `PATCH`/`DELETE` works identically on every one of the 11 other resources tested (categories, attribute groups/attributes, connections, import profiles, product/asset lists, channels). Explains the pattern and points to the API Reference tab's dedicated reference page for the full per-resource list. **Flagged**: Plytix hasn't confirmed whether this is a stable, intentional part of the public API or an implementation detail that could change — say so plainly rather than presenting it as guaranteed.
* **Static & Smart List Membership** [`Concept`]: Neither list-creation endpoint has a member-ID field — a "Static" list is actually a Smart list whose auto-generated query matches the list's own id, and real membership lives on each product's/asset's own `static_list_ids` field. This mechanism appears nowhere in the raw materials or Help Center and was only discovered through live testing; explains how to add/remove members via `PATCH` on the product/asset, not the list.

### Integration Guides

Solution-oriented how-to content for the real workflows Plytix's own product team and 614 logged customer-feedback entries identify as what developers actually build, grounded in `materials/project-references/before-writing.md`'s "Jobs to Be Done" list.

* **Syncing Your ERP with Plytix** [`How-to Guide`]: The most common real-world use case per both kickoff calls and the JTBD list's #2 — reading product data from Plytix to push to an ERP, and pushing price/stock/status updates back. Notes the open v1/v2-vs-v3 write question from Getting Started applies directly here.
* **Exporting Your Full Catalog** [`How-to Guide`]: Paginating through every product with attributes and assets in one operation (JTBD #3) — the workflow v3's automatic asset/category expansion and removal of v1/v2's 50-attribute limit was built to solve, per `before-writing.md`. Primary audience: catalog-production tools like EasyCatalog, platform migrations, backups.
* **Auditing Product Data Quality with Filters** [`How-to Guide`]: Finding products with missing GTINs, missing images, or empty descriptions using completeness and relationship filters (JTBD #5). Explicitly framed as "here's what you can now do," not an advanced/optional topic — Plytix's own filter-usage analysis found these filters are barely discovered (relationship filters: 43 of 749 active accounts) despite clear need, not because they're unwanted.
* **Building Channel-Specific Product Feeds** [`How-to Guide`]: Filtering a product set for a specific channel or marketplace (JTBD #6) and wiring it to a Channel via `product_list_id`. Also documents the confirmed-live Channels resource itself (format enum, rebuild-schedule fields) — see Sources & Corrections for why this supersedes the previous assumption that Channels aren't API-accessible.
* **Safely Removing Categories, Assets, or Relationships from a Product** [`How-to Guide`]: A dedicated safety-focused guide built specifically because of a confirmed, reproducible hazard: `DELETE /products/{id}/{subpath}` doesn't do a scoped removal — it deletes the whole product, silently, regardless of what `{subpath}` is. Documents the only confirmed-working alternative (`PATCH` with a reduced array) and states plainly that no other unassign mechanism exists yet.
* **Reconstructing Parent/Variant Hierarchies** [`How-to Guide`]: Retrieving a parent product and its variants in a structured way, resolving `product_level` (0 → standalone, 1 → parent, 2 → variant, set automatically, not at creation) and `num_variations` (JTBD #7). Notes Product Families/Family Models themselves are read-only via the API — the family must already exist, created from the dashboard.
* **Bulk Operations for Large Catalogs** [`How-to Guide`]: The currently-implemented, job-based `POST /api/v1/bulk/products` mechanism (per-SKU error reporting, up to 1000 products/call) from `Bulks Documentation (API) (Limited to Large Clients).pdf`. **Flagged as enterprise/restricted**: the v1 bulk API isn't offered on lower-tier plans, and per customer feedback (`before-writing.md`, `API_Feedback_-_From_Product_board.pdf`), its error responses don't distinguish a skipped-no-change product from a silently-failed one — a known, real pain point worth naming rather than glossing over. Kept clearly separate from the *unimplemented* v3 bulk/`-jobs`/Process Manager scheme `API V3.md` describes in prose (see Sources & Corrections).
* **Getting Notified: Webhooks & Automations** [`Concept`]: Clarifies three distinct "webhook" concepts so a reader doesn't conflate them: (1) the in-app, dashboard-configured "channel processed" webhook the Help Center documents, entered through the "automations" feature; (2) an optional callback-URL field on a v3 bulk/async job payload described in `API V3.md`'s (unimplemented) prose; (3) a dedicated, currently-in-progress "Webhooks" project Plytix's own roadmap names as a future real-time alternative to polling. None of these is a general-purpose, subscribable v3 API webhook today — say so plainly rather than implying one exists.

### Destinations (Coming Soon)

* **Destinations: What's Coming** [`Concept`]: A single roadmap-flagged page for Plytix's stated upcoming "Destinations" mechanism — a new, unified way to see and manage which channels, Brand Portals, and Product Data Sheets a product is assigned to, exposed as filterable/writable API fields. Explicitly **not** a replacement for the Channels resource documented today (see Sources & Corrections) — this page exists so a reader who's heard the term doesn't go looking for it in the current API.

### Plytix MCP

A dedicated section per the Project Requirements doc's explicit ask, and confirmed as a real near-term priority in `before-writing.md`'s roadmap ("a significant differentiator for the developer audience"). **Flagged: still in progress** — verify content against the shipped implementation before publishing.

* **What Is the Plytix MCP?** [`Concept`]: Overview and capabilities — what an MCP-connected AI assistant (Claude, Cursor, Windsurf, VS Code, Gemini) can do against a Plytix account.
* **Setting Up the Plytix MCP** [`How-to Guide`]: Setup and authentication steps for connecting an MCP client to a Plytix account.
* **Available Tools & Supported Clients** [`Reference`]: The MCP's tool surface and which AI clients are officially supported.
* **MCP Examples & Common Use Cases** [`How-to Guide`]: Worked examples such as curating and importing a product catalog through an AI assistant.

### SDKs & CLI

* **Official SDKs & CLI (Coming Soon)** [`Concept`]: A placeholder page stating that type-safe API v3 SDKs and a CLI are on the roadmap but not yet released. Deliberately left without installation/usage instructions until real SDKs exist.

Precise, exhaustive technical reference: authentication, conventions, errors, limits, query syntax, and one auto-generated page per API resource. Partially wired already in `docs.json` (`api-reference/openapi.json`, a copy of the root `openapi_pimv3.json` with an added `servers` entry and bearer-auth security scheme).

### Overview & Conventions

* **API Reference Overview** [`Concept`]: Orients the reader to the auto-generated reference and how this tab relates to the Guides tab's conceptual explanations. Already drafted at `docs/guides/api-overview.mdx`; its card grid of resources should add Destinations once that ships and keep noting Relationships/Product Families/Product Family Models as read-only.
* **Authentication** [`Reference`]: Exact bearer-token request/response shapes and the confirmed 15-minute token lifetime (verified two ways: Plytix's own product team statement and the live JWT's `exp`−`iat` claim). Already drafted at `docs/guides/authentication.mdx`, but its error-response table needs correcting — the documented `{"msg": "Bad api_key or api_password"}` 401 shape doesn't match what the live endpoint actually returns (see Sources & Corrections). Should also note the undocumented `refresh_token` field returned alongside `access_token`, flagged as unconfirmed whether it's usable.
* **Errors & Status Codes** [`Reference`]: Needs a substantial rewrite from the current draft (`docs/guides/status-codes.mdx`), which documents a `detail`/`HTTPValidationError`/`ValidationError` shape for 422s that was never once observed live. Replace with the three confirmed real error-shape families (auth's nested `error`, the flat `errors: [{name, description}]` array used almost everywhere else, and note that a single response can carry multiple `errors` entries at once — confirmed on list-resource creation). Document real confirmed status codes per operation type (`201` create, `204` delete, `200` for most `PATCH`, with named resource-level exceptions), explicitly contrasted with the spec's declared `200`/`422`-only responses.
* **Rate Limits** [`Reference`]: Now has real numbers instead of none — but two different confirmed values must both be presented with their source and scope, not silently picked between: live JWT claims put the tested "API Docs" account at 20 req/10s / 15,000 req/hour and the "Dev" account at 20 req/10s / 5,000 req/hour, while `before-writing.md` (sourced from a support escalation) cites 50 req/10s / 5,000 req/hour. Present rate limits as **plan-dependent**, give the confirmed per-account examples as illustrations, and point readers to their account manager for their exact plan limit rather than asserting one universal number. Needs a rewrite from the current draft (`docs/guides/rate-limits.mdx`), which currently states no numeric thresholds were found at all.
* **Filtering & Query Syntax Reference** [`Reference`]: The full confirmed-live operator, grouping (`_and`/`_or`/`_not`/`_!exists`), related-entity dot-filter (`categories.name=`), and custom-attribute filter (`attributes.<name>=`) tables — using the confirmed **query-string dialect** (`API V3.md`'s "Possible Alternative" column), not the JSON-object dialect the prose labels "Current." Also documents that `_expand` doesn't exist on `/products` (contradicting `API V3.md`) — expansion happens automatically per `_fields` instead.
* **Pagination Reference** [`Reference`]: Documents the confirmed default page size (25), the link-style `pagination.next_page` mechanism, and that `_page`/`_page_size` work while `_offset`/`_limit` (one of `API V3.md`'s two "Possible Alternative" pagination styles) does not — a live `400`, not just an unconfirmed claim.
* **Undeclared Write Operations Reference** [`Reference`]: A new reference page this project's live testing makes necessary — since `openapi_pimv3.json` doesn't declare `PATCH`/`DELETE` on most writable resources, Mintlify's auto-generated reference pages won't show them at all. Lists, per resource, which undeclared methods are confirmed working (11 of 11 tested resources support both), the shared `{identifier}` route pattern, and the specific subpath-`PATCH` body-shape convention (`{path}` names a field; the body is that field's raw new value, not a partial object).

## User Navigation Flow

Designed for an Integration Engineer building an ERP-to-Plytix connection for the first time. "Winning" means successfully reading real product data and applying a confirmed write back through the API using their own data.

1. **Get Started with the API** → Generates an API key, exchanges it for a bearer token, and confirms the connection with a first `GET /products` call.
2. **The Plytix Data Model** → Understands how Products, Attributes, Categories, and Assets relate before writing any integration code.
3. **Filtering, Sorting & Pagination** (Core Concepts) → Learns the `in`/`eq`/`exists`/`like` operators and OR-logic needed to search and page through product data.
4. **Products** (API Reference, auto-generated) → Looks up the exact parameters for `GET /api/v3/products` and confirms which fields are safe to filter/expand.
5. **Choosing Between v1/v2 and v3** → Confirms which API version to write through for their specific workflow before building anything that mutates data.
6. **Syncing Your ERP with Plytix** (Integration Guides) → Applies the general read/write pattern to their own ERP-to-Plytix use case, using SKU as the matching key.
7. **First win** → Successfully retrieves their ERP's products from `GET /api/v3/products` and applies an update via `PATCH /api/v3/products/{identifier}`, receiving a confirmed `200` back with their own data reflected — their first real, working connection between the two systems.
