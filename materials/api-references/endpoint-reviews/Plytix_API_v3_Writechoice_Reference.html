02 / Retained decisions

Documentation principles

Field selection and expansions

Use repeated _fields parameters to select fields and expand related entities. A to-one relation resolves to an object and a to-many relation to a list. The audit marks expandable relations separately from default fields.

Expansion results

The approved design returns all elements of an expanded relation, even when the search filters use that relation. Filtering selects parent results; it does not trim the expanded list.

Resolved product values

The audit specifies resolved values for custom attributes, including inheritance, formulas and completeness. Inheritable system attributes also return their resolved values.

Variants and family assignment

parent_id and product_family_id are accepted on product creation and update. The spec describes null on PATCH as detaching the parent or unassigning the family.

Dedicated association operations

Categories, static lists and attribute groups are linked and unlinked through dedicated POST and DELETE routes, rather than by writing denormalized ID lists in the entity body.

Category hierarchy

Category parent_id and order are writable in the audit. The direct parent and ancestors are expandable. Product-category path is omitted from the agreed field matrix pending its final public exposure decision.

Families and attribute levels

Product Families are the public family concept. The audit uses family_attributes associations to assign attributes and their level. A separate Product Family Models resource is outside the v3 public model.

Asset inputs and outputs

The audit targets basic asset data plus a download URL. The current spec accepts either a remote url or base64 content on creation; filename is required with content. These names differ from the audit input downloaded_from.

Public field boundary

The audit excludes account identifiers, user audit data, denormalized ID arrays, counters and housekeeping fields from public DTOs. Product status remains a public field. Use the entity matrix for precise field decisions.

Attribute definitions

Field availability depends on attribute type. The audit retains formula_str, removes the parsed formula tree and replaces legacy attribute-group label lists with related attributes.

03 / Reference and implementation alignment

OpenAPI alignment

The items below compare the field model in this document with current OpenAPI declarations. Verify these differences before publishing the affected examples.

Public resource boundary

The audit excludes channels, connections, e-catalogs, PDF catalogs and import profiles. The raw spec still declares CRUD routes for these resources and some product association routes.

Agency action: Exclude these domains and their associations from public reference generation; raw-spec presence is not publication approval.

Relationship naming and shape

The audit uses product-relationship_types and directional product_relationships_to/from with from/to fields. The spec uses /relationships, product_relationships, relationship_id and related_products.

Agency action: Use exact spec paths for implementation checks. Keep directional audit payloads and route examples out of published tutorials until the field model and implementation are aligned.

Product fields and nullability

The audit marks sku editable, but ProductUpdateInputDto has no sku. It allows null for gtin/status at model level; PATCH schemas for these fields are non-nullable. ProductOutputDto also declares num_variations and overwritten_attributes, excluded by the audit.

Agency action: Verify operation-specific request schemas and final output filtering. Do not infer PATCH support or nullability from the model-level audit.

Asset creation and metadata

The audit uses downloaded_from as create input and hides file metadata/counters. AssetCreateInputDto instead uses url or content. AssetOutputDto declares several metadata and internal fields excluded by the audit.

Agency action: Use the current creation schema for working examples; verify the intended reduced public output before publication.

Family creation and identifier

The audit creates families with name and manages attributes through associations. ProductFamilyCreateInputDto still accepts attributes, parent_attributes and variant_attributes. ProductFamilyOutputDto declares _id and counters; the audit uses id and hides counters.

Agency action: Align family request/output schemas with the audit. Document Product Families only; do not introduce a Family Models concept.

Attribute-group output

The audit replaces attribute_labels with related attributes. ProductAttributeGroupOutputDto still declares attribute_labels and has no attributes property.

Agency action: Verify the replacement field and its response shape before publishing the new group example.

Incomplete association schemas

POST operations for product relationship collections and family attribute collections are present, but their OpenAPI operations do not declare a requestBody.

Agency action: Complete the input schema before generating payload examples from these operations. The field matrix uses U for this untyped input.

Category output and public path

The audit hides slug and n_children and leaves product-category path outside the confirmed set. ProductCategoryGetOutputDto declares all three.

Agency action: Apply the agreed output filter to slug and n_children; keep path out of confirmed guidance until its exposure is settled.

04 / Reference patterns

Conventions and examples

Pagination

_page starts at 1. _page_size defaults to 25, with a declared maximum of 1000. Follow pagination.next_page until there is no next link. The current Pagination schema declares next_page and previous_page only.

Sorting

Repeat _sort_by to sort by multiple fields, in parameter order. Prefix a field with - for descending order.

Filters

The current spec describes field=value and field[operator]=value, repeated in/intersects filters, grouping with _or[N] and _and[N], negated forms, and functions such as lower, length and days_passed. Entity-level and public restrictions still apply.

Safe examples

Use the four product examples below as syntax references. Validate exact returned shapes and supported field paths against the running release before publishing screenshots or complete response examples.

Mutations

Use each operation's declared status and schema. Product create declares 201; product PATCH and DELETE declare 204. Do not generalize a response body from a design template.

Empty values and deletion

The design distinguishes an explicit empty string or empty list from deletion. DELETE removes the addressed entity or field; it does not mean setting null or applying a default. Applicable routes govern support.

Select product fields

GET /api/v3/products?_fields=sku&_fields=status

Expand product categories

GET /api/v3/products?_fields=sku&_fields=categories.*

Page and sort results

GET /api/v3/products?_page=2&_page_size=50&_sort_by=-sku

Combine filters

GET /api/v3/products?status=Draft&label[contains:ignorecase]=shirt

Query strings are shown in readable form. Encode reserved characters when constructing request URLs. The examples illustrate syntax; they are not recorded test results.

05 / Field audit

Entity reference

Each triple reads Create / Edit / Read. In audit columns: Y = writable; D = default read field under the audit; X = expandable; - = excluded for that operation; n/a = absent from the v1 baseline. In the spec column: S = property declared in a schema; - = not declared; U = input schema not declared at that route.

The spec column checks direct request schemas and search-result item schemas. It records presence, not exact type compatibility or default serialization. Attribute-type unions are combined. Family-attribute and relationship collection writes are untyped in the snapshot. For attributes.<attribute_label>, presence refers to its attributes container. Model types below come from the audit; use request schemas for per-operation requiredness and nullability.

06 / Publication scope

Scope exclusions

Outside public v3 scope

Channels; connections; e-catalogs; PDF catalogs; import profiles; their product links. Internal infrastructure routes must also be filtered from the public specification.

Family Models

Legacy storage concept only. The public model exposes Product Families.

Bulk and asynchronous design

Bulk and job-management operations are not declared in the current OpenAPI snapshot. Keep these operations outside current implementation examples.

Other bulk services

Legacy V1 Bulk API documentation remains private under the project publication decision. Bulk exports are a separate service/topic and are not defined by this field-audit handoff.
