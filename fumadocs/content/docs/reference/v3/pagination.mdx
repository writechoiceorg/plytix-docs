Search endpoints return results in pages. This page documents the pagination block in the response, how to walk through a result set, and the request parameters that control page size and sort order.

Key points on this page:

- Every search response carries a `pagination` object alongside `data` and `errors`.
- The confirmed way to page is to follow `next_page` until it comes back null.
- `pagination` is null on responses that aren't searches, such as getting one record.
- Request parameters for page size and sorting aren't in the spec yet, so treat them as unconfirmed.

## The search response envelope

Every search response uses the same envelope:

```json
{
  "data": [],
  "errors": [],
  "pagination": {
    "next_page": null,
    "previous_page": null
  }
}
```

| Field | Type | Description |
|---|---|---|
| `data` | array | The records matching your query |
| `errors` | array of `Error` | Always present, empty when there's nothing to report |
| `pagination` | object or null | Present on searches, null on operations that return a single record |

The `pagination` object has two fields, both of which can be null:

| Field | Type | Description |
|---|---|---|
| `next_page` | string or null | URL of the next page. Null on the last page |
| `previous_page` | string or null | URL of the previous page. Null on the first page |

## Page through a result set

v3 returns page URLs rather than a page number to increment. Request the first page, then follow `next_page` until it's null:

```bash
# First page
curl --request GET \
  --url 'https://<v3-base-url>/api/v3/products?status=Draft' \
  --header 'Authorization: Bearer <token>'

# Then request the URL in pagination.next_page, and repeat
# until next_page comes back null.
```

A loop in pseudocode:

```text
url = "/api/v3/products?status=Draft"
while url is not null:
    response = GET url
    process(response.data)
    url = response.pagination.next_page
```

<Callout type="info" title="Follow the URL, don't rebuild it">
  `next_page` carries your filters and sort order forward. Rebuilding the URL by incrementing a page number risks dropping a parameter, and it breaks if Plytix changes the paging mechanism later. Use the URL you're given.
</Callout>

## Page without surprises

- **Don't assume a total.** The confirmed pagination block carries no count, so the only reliable way to know how many records matched is to page to the end and tally as you go.
- **Watch the request rate.** Paging through a large result set is many requests in quick succession. Rate limits vary by account and are carried in your access token's claims, so pace a long loop and back off on `429`. See [Rate limits](/docs/reference/v3/rate-limits).
- **Ask for fewer fields.** `_fields` narrows each record to what you need, which makes a long paging run noticeably cheaper. See [Filtering and Query Syntax](/docs/reference/v3/filtering-query-syntax).
- **Expect the set to shift under you.** A catalog that changes mid-run can move records between pages. For an export that has to be internally consistent, filter on a stable field such as a date range rather than paging an unfiltered set.
