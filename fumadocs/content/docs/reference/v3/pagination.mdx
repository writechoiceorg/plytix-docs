Search endpoints return results in pages. This page documents the pagination block in the response, how to walk through a result set, and the request parameters that control page size and sort order.

Key points on this page:

- Every search response carries a `pagination` object alongside `data` and `errors`.
- Page by following `next_page` until the key is no longer present.
- The pagination keys are **omitted** when they don't apply. They are never `null`.
- There is no record count of any kind. To size a result set, page to the end and tally.
- The links come back as `http://` URLs, which can cost you your auth header. See [Fix the scheme before following the link](#fix-the-scheme-before-following-the-link).

## The search response envelope

Every search response uses the same envelope:

```json
{
  "data": [],
  "errors": [],
  "pagination": {
    "next_page": "http://<v3-base-url>/api/v3/products?_page=2"
  }
}
```

| Field | Type | Description |
|---|---|---|
| `data` | array | The records matching your query |
| `errors` | array of `Error` | Always present, empty when there's nothing to report |
| `pagination` | object | Present on searches, absent on operations that return a single record |

The `pagination` object holds up to two keys:

| Field | Type | Description |
|---|---|---|
| `next_page` | string | URL of the next page. Absent on the last page |
| `previous_page` | string | URL of the previous page. Absent on the first page |

<Callout type="warn" title="The keys are absent, not null">
  When a link doesn't apply, the application leaves the key out rather than setting it to `null`. A client written as `if (pagination.next_page !== null)` will loop forever, because the key is `undefined` on the last page, not `null`. Test for presence or truthiness instead.
</Callout>

So the object you get back depends on where you are in the result set:

| Where you are | What `pagination` contains |
|---|---|
| First page of several | `next_page` only |
| A middle page | Both keys |
| The last page | `previous_page` only |
| The result set fits on one page | `{}` an empty object |
| A page past the end | `previous_page` only, with `data: []` and status `200` |
| Getting a single record | No `pagination` key at all, and `data` is an object |

## Page through a result set

The application returns page URLs rather than a page number to increment. Request the first page, then follow `next_page` until the key stops appearing:

```bash
# First page
curl --request GET \
  --url 'https://<v3-base-url>/api/v3/products?status=Draft' \
  --header 'Authorization: Bearer <token>'

# Then request the URL in pagination.next_page, and repeat
# until the response has no next_page key.
```

A loop in pseudocode:

```text
url = "/api/v3/products?status=Draft"
while url:
    response = GET url
    process(response.data)
    url = response.pagination.get("next_page")   # absent on the last page
    if url: url = url.replace("http://", "https://")
```

### Fix the scheme before following the link

`next_page` carries your filters and sort order forward, so following it beats rebuilding the URL yourself: incrementing a page number risks dropping a parameter.

The application generates these links with the `http` scheme:

```json
"next_page": "http://<v3-base-url>/api/v3/products?_page=2"
```

Requesting that URL as given returns a `301` redirect to the `https` address. Many HTTP clients drop the `Authorization` header when a redirect changes the scheme, so the redirected request arrives unauthenticated and you get:

```json
{ "detail": "Unauthorized" }
```

Rewrite the scheme to `https` before you request the URL.

## Request parameters

Use these three parameters to control paging and sort order:

| Parameter | Type | Description |
|---|---|---|
| `_page` | integer | The page to return. Must be 1 or greater. Defaults to `1` |
| `_page_size` | integer | Records per page. Maximum `1000`. Defaults to `25` |
| `_sort_by` | string | Field to sort by. Prefix with `-` for descending |

Both bounds are enforced, and the error names the parameter and the limit. `_page=0` returns:

```json
{
  "data": [],
  "errors": [
    {
      "name": "InputDTOValidationError",
      "description": "query._page: Input should be greater than or equal to 1"
    }
  ]
}
```

`_page_size=1001` returns the same shape with `"query._page_size: Input should be less than or equal to 1000"`.

### There are no count parameters

The application doesn't return a count of matching records, and there is no parameter that asks for one. `_total_count` and `_filtered_count` each return `400`:

```json
{
  "data": [],
  "errors": [
    {
      "name": "InvalidFieldError",
      "description": "Field '_total_count' does not exist."
    }
  ]
}
```

The pagination block carries no counts either. This is a difference from V1, whose search responses included `total_count`. If you're migrating, see [Migrating to V3](/docs/guides/migrating-to-v3).

## Page through results safely

Keep these points in mind when you page through a large result set:

- **Don't assume a total.** The pagination block carries no count, so the only reliable way to know how many records matched is to page to the end and tally as you go. For a set you know is small, `_page_size=1000` gets you everything in one request.
- **Watch the request rate.** Paging through a large result set is many requests in rapid succession. Rate limits vary by account and are carried in your access token's claims, so pace a long loop and back off on `429`. See [Rate limits](/docs/reference/v3/rate-limits).
- **Ask for fewer fields.** `_fields` narrows each record to what you need, which makes a long paging run noticeably cheaper. See [Filtering and Query Syntax](/docs/reference/v3/filtering-query-syntax).
- **Expect the set to shift under you.** A catalog that changes mid-run can move records between pages. For an export that has to be internally consistent, filter on a stable field such as a date range rather than paging an unfiltered set.
