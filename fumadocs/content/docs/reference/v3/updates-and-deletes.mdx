This page documents which method to use for each kind of change, what comes back in the response, how empty values are treated, and what DELETE removes.

Key points on this page:

- POST returns the full created record. PATCH returns `204` with no body, so an update has to be read back.
- PATCH is the standard way to change a record, because it touches only the top-level fields you name.
- Naming a map field such as `attributes` in a PATCH on the record replaces that whole map, deleting anything you left out. A partial map sent to `PATCH .../attributes` is merged instead.
- On the attribute types tested, sending `""`, `[]`, or `null` clears the value, so the attribute ends up absent rather than stored as empty.
- DELETE erases a field or record rather than setting it to null. Erasing a variant's value doesn't bring back an inherited value.

## Choose a method

| Goal | Method | Path |
|---|---|---|
| Create a record | POST | `/api/v3/<entities>` |
| Change some fields on a record | PATCH | `/api/v3/<entities>/<identifier>` |
| Remove a record | DELETE | `/api/v3/<entities>/<identifier>` |
| Read, create, change, or remove a single field | GET, POST, PATCH, DELETE | `/api/v3/<entities>/<identifier>/<field>` |
| Link a related record | POST | `/api/v3/<entities>/<identifier>/<related-entities>` |
| Change a link | PATCH | `/api/v3/<entities>/<identifier>/<related-entities>/<linked_id>` |
| Remove a link | DELETE | `/api/v3/<entities>/<identifier>/<related-entities>/<linked_id>` |

`<identifier>` is usually the record's ID. For products, a URL-encoded SKU works too, and an identifier that matches nothing returns `404`.

<Callout type="info" title="Why PATCH rather than PUT">
  PATCH names only the fields you're changing, which reduces the risk of overwriting a field you didn't mean to touch and makes concurrent edits safer.
</Callout>

## What a write returns

A successful POST returns the complete created record. PATCH and DELETE return no body at all, so the only way to see the result of an update is to read the record back.

| Operation | Status | Body |
|---|---|---|
| Create | `201` | The full created record |
| Update | `204` | None |
| Delete | `204` | None |
| Accepted for async processing | `202` | A `process_id` for tracking |

## What a PATCH replaces

A PATCH on a record merges at the top level only. Top-level fields you leave out keep their current values, but a map field you name is replaced in full rather than merged into.

| What you send | What happens |
|---|---|
| A top-level field (`label`, `status`, `gtin`) | Only that field changes |
| A top-level field you omit | Left untouched |
| `attributes` with some keys, to `PATCH /products/<identifier>` | The whole map is replaced; omitted attributes are deleted |
| A partial map, to `PATCH /products/<identifier>/attributes` | The attributes you send are merged; omitted attributes are kept |

So `{"attributes": {"suggested_retail_price": "34.99"}}` sent to the product leaves a product that also has `brand` and `collection` with `suggested_retail_price` alone. To change several attributes and keep the rest, send the partial map, `{"suggested_retail_price": "34.99"}`, to the product's `attributes` path instead. [Responses and updates](/docs/guides/migrating-to-v3/responses-and-updates#how-patch-treats-the-attributes-map) shows both routes with before and after examples.

To change one attribute, address it through its own path. The body is the bare value, in the format the attribute type takes. A decimal attribute takes its value as a string:

```bash
curl --request PATCH \
  --url 'https://<v3-base-url>/api/v3/products/<identifier>/attributes/<name>' \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '"34.99"'
```

This returns `204` and leaves every other attribute intact.

## How empty values are treated

On the attribute types tested, an empty value isn't stored. A text attribute set to `""`, `null`, or only spaces, and a multiselect attribute set to `[]` or `null`, end up absent from the product, the same as an attribute that was never set. A media gallery set to `[]` or `null` loses its asset associations, while the assets stay in Plytix DAM. A media attribute rejects `""`, so clear it with DELETE on its field path.

A cleared attribute and one that was never set both match `[!exists]=true` and `[length]=0`, and neither matches `[null]`. Other attribute types haven't been tested. [Responses and updates](/docs/guides/migrating-to-v3/responses-and-updates#empty-values-null-and-deletion) lists the tested cases by type.

## What DELETE removes

DELETE erases the thing it's applied to. It doesn't set the value to null and it doesn't restore a default.

```bash
# Removes the record
curl --request DELETE \
  --url 'https://<v3-base-url>/api/v3/products/<identifier>' \
  --header 'Authorization: Bearer <token>'
```

<Callout type="warn" title="Erasing a variant's value doesn't restore inheritance">
  In testing, deleting a value that a variant had overridden left the variant with no value for that attribute. It didn't bring back the parent's value, and the attribute stayed listed in the variant's `overwritten_attributes` array. Check on a test record before running a delete across a catalog.
</Callout>

Field-level writes apply to attributes only. You can POST, PATCH, or DELETE a single attribute on a record through its field path; other fields are changed with PATCH on the record.

## Change a single field

V3 exposes fields as paths under a record, so you can read or change one field without sending the whole record:

```bash
# Read one field
curl --request GET \
  --url 'https://<v3-base-url>/api/v3/products/<identifier>/<field>' \
  --header 'Authorization: Bearer <token>'
```

The same path pattern extends through related entities, in the form `/api/v3/<entities>/<identifier>/<subentity>/<identifier>/<field>`.

## Advanced updates

Some changes can't be expressed by assigning a value to a field, such as inserting an item at a specific position in a list. For those, V3 accepts JSON Patch: send a PATCH with the content type `application/json-patch+json` and a body that describes the change as a list of RFC 6902 operations, each naming an `op`, a `path`, and, where the operation needs one, a `value`.

## Async operations

An operation that can't complete within the request returns `202` with a `process_id` rather than a result. Track it through the Process Manager API, and the record changes once processing finishes.

## Write safely

Follow these practices when you write to the API:

- **Read before you write.** Confirm which records match your filter before applying a change to them.
- **Test deletes on one record.** Erasure and inheritance interact in ways that are hard to predict from a filter alone.
- **Don't parse a write response for values.** Read the record back instead.
- **Pace a long run of writes.** V3 has no bulk write endpoints, so a large change is many single requests. See [Rate limits](/reference/v3/rate-limits).
