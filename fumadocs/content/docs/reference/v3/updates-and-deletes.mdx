This page documents which method to use for each kind of change, what comes back in the response, how empty values are treated, and what DELETE removes.

Key points on this page:

- POST returns the full created record. PATCH returns `204` with no body, so an update has to be read back.
- PATCH is the standard way to change a record, because it touches only the top-level fields you name.
- Naming a map field such as `attributes` in a PATCH replaces that whole map, deleting anything you left out.
- An empty string or empty list is stored as a value, not treated as a deletion.
- DELETE erases a field or record rather than setting it to null, which can let an inherited value take over.

## Choose a method

| Goal | Method | Path |
|---|---|---|
| Create a record | POST | `/api/v3/<entities>` |
| Change some fields on a record | PATCH | `/api/v3/<entities>/<identifier>` |
| Remove a record | DELETE | `/api/v3/<entities>/<identifier>` |
| Read, create, or remove a single field | GET, POST, DELETE | `/api/v3/<entities>/<identifier>/<field>` |
| Link a related record | POST | `/api/v3/<entities>/<identifier>/<related-entities>` |
| Change a link | PATCH | `/api/v3/<entities>/<identifier>/<related-entities>/<linked_id>` |
| Remove a link | DELETE | `/api/v3/<entities>/<identifier>/<related-entities>/<linked_id>` |

`<identifier>` is usually the record's ID. For products, a URL-encoded SKU works too, and an identifier that matches nothing returns `404`.

<Callout type="info" title="Why PATCH rather than PUT">
  PATCH names only the fields you're changing, which reduces the risk of overwriting a field you didn't mean to touch and makes concurrent edits safer.
</Callout>

## What a write returns

A successful POST returns the complete created record. PATCH and DELETE return no body at all, so the only way to see the result of an update is to read the record back.

| Operation | Status | Body |
|---|---|---|
| Create | `201` | The full created record |
| Update | `204` | None |
| Delete | `204` | None |
| Accepted for async processing | `202` | A `process_id` for tracking |

## What a PATCH replaces

A PATCH merges at the top level only. Top-level fields you leave out keep their current values, but a map field you name is replaced in full rather than merged into.

| What you send | What happens |
|---|---|
| A top-level field (`label`, `status`, `gtin`) | Only that field changes |
| A top-level field you omit | Left untouched |
| `attributes` with some keys | The whole map is replaced; omitted attributes are deleted |

So `{"attributes": {"price": 34.99}}` on a product that also has `brand` and `care_instructions` leaves it with `price` alone. Read the current map, apply your change to it, and send the result back.

To change one attribute without resending the map, address it through its own path instead. The body is the bare value:

```bash
curl --request PATCH \
  --url 'https://<v3-base-url>/api/v3/products/<identifier>/attributes/<name>' \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '34.99'
```

This returns `204` and leaves every other attribute intact.

## How empty values are treated

An empty string or an empty list is a value in v3, not an instruction to remove something.

| Operation | Empty value behavior |
|---|---|
| POST | `""` and `[]` are stored verbatim |
| PATCH | `""` and `[]` are stored verbatim |
| DELETE | Erases the field or record |

So `{"description": ""}` sets the description to an empty string. It doesn't remove the field. To remove it, use DELETE on the field path.

## What DELETE removes

DELETE erases the thing it's applied to. It doesn't set the value to null and it doesn't restore a default.

```bash
# Removes the record
curl --request DELETE \
  --url 'https://<v3-base-url>/api/v3/products/<identifier>' \
  --header 'Authorization: Bearer <token>'
```

<Callout type="warn" title="Erasing a field can change what the record shows">
  Because DELETE erases rather than nulls, removing a field can let an inherited value resolve in its place. A product that inherits from a family may show the family's value once its own is gone, so the field doesn't go empty, it changes. Check on a test record before running a delete across a catalog.
</Callout>

Field-level creation and deletion apply to attributes only. You can POST or DELETE a single attribute on a record through its field path; other fields are changed with PATCH on the record.

## Change a single field

V3 exposes fields as paths under a record, so you can read or change one field without sending the whole record:

```bash
# Read one field
curl --request GET \
  --url 'https://<v3-base-url>/api/v3/products/<identifier>/<field>' \
  --header 'Authorization: Bearer <token>'
```

The same path pattern extends through related entities, in the form `/api/v3/<entities>/<identifier>/<subentity>/<identifier>/<field>`.

## Advanced updates

Some changes can't be expressed by assigning a value to a field, such as inserting an item at a specific position in a list. For those, v3 accepts JSON Patch: send a PATCH with the content type `application/json-patch+json` and a body that describes the change as a list of RFC 6902 operations, each naming an `op`, a `path`, and, where the operation needs one, a `value`.

## Async operations

An operation that can't complete within the request returns `202` with a `process_id` rather than a result. Track it through the Process Manager API, and the record changes once processing finishes.

## Write safely

- **Read before you write.** Confirm which records match your filter before applying a change to them.
- **Test deletes on one record.** Erasure and inheritance interact in ways that are hard to predict from a filter alone.
- **Don't parse a write response for values.** Read the record back instead.
- **Pace a long run of writes.** V3 has no bulk write endpoints, so a large change is many single requests. See [Bulk operations for large catalogs](/docs/guides/bulk-operations-for-large-catalogs).
