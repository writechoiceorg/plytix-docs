Pull your entire product catalog, with attributes and assets included, without a separate call per product or per image. This guide covers paging through a large result set and expanding related data inline, the pattern behind tools like catalog-production plugins, platform migrations, and backups. All requests use the V3 API with a bearer token. Access tokens expire after 15 minutes, so a long export can start returning `401` partway through. If that happens, request a new token and resume from the page you were on.

## Prerequisites

Before you start, make sure you have the following:

- A bearer token. See [Authentication](/docs/reference/v3/authentication), or the [Quickstart](/docs/guides/quickstart) for a first walkthrough.
- An idea of which fields you actually need. Requesting only those fields keeps each page smaller and the export faster.

## Export the catalog page by page

Follow the steps below to request the fields you need, walk the pages until you reach the end, and read related data straight out of each product.

1. **Request the first page with the fields you need.**

   ```bash
   curl -G "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     --data-urlencode "_fields=sku" \
     --data-urlencode "_fields=label" \
     --data-urlencode "_fields=attributes" \
     --data-urlencode "_fields=categories" \
     --data-urlencode "_fields=assets" \
     --data-urlencode "_page_size=100"
   ```

   `_fields` accepts repeated values. Requesting `categories` or `assets` returns them fully expanded, with no separate call needed.

   Don't add `_expand`. The V3 search endpoint rejects it with `400` and `"Field '_expand' does not exist in model 'Product'."` Expansion happens automatically for each `_fields` value you name.

2. **Follow the `next_page` link until it stops appearing.**

   Every response includes a `pagination` object:

   ```json
   {
     "data": [ /* ... */ ],
     "pagination": { "next_page": "http://pim.plytix.com/api/v3/products?_fields=sku&_page=2" }
   }
   ```

   Request `pagination.next_page` directly. It's a complete URL, including every filter and field you sent on the first call. The default page size is 25; the maximum is 1000, so setting `_page_size` explicitly (as in step 1) cuts the number of requests for a large catalog substantially. Stop when a response has no `next_page` key: on the last page the key is absent, not `null`. The V3 search endpoint has no total count, so plan progress reporting around pages rather than a percentage. See [Pagination](/docs/reference/v3/pagination) for the full rules.

   <Callout type="warn" title="Rewrite the link to https before you request it">
     Plytix generates these links with the `http` scheme. That address `301`-redirects to `https`, and many HTTP clients drop the `Authorization` header across a scheme change, so the redirected request comes back `401 {"detail": "Unauthorized"}`. Swap `http://` for `https://` before requesting the URL, or configure your client to keep the auth header across redirects (`curl --location-trusted`).

     This bites hardest on a long export loop, where the first page succeeds and page two fails for no obvious reason.
   </Callout>

3. **Read the expanded asset and category data directly from each product.**

   ```json
   {
     "sku": "BAG-10157",
     "categories": [{ "id": "...", "name": "Backpacks", "path": ["Website Taxonomy", "Bags & Luggage", "Backpacks"] }],
     "assets": [{ "id": "...", "content_type": "image/jpeg", "path": "..." }]
   }
   ```

   Because `assets` returns the full asset object, including its file path, your export doesn't need a separate request per image.

4. **Scope the export if you don't need the whole catalog.**

   Combine `_fields` with a filter, for example to export only one category:

   ```bash
   curl -G "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     --data-urlencode "categories.name=Backpacks" \
     --data-urlencode "_fields=sku"
   ```

   See [Build a marketplace-specific product feed](/docs/guides/building-marketplace-specific-product-feeds) for more filtering patterns aimed at a specific audience or destination.

## Troubleshooting

Check the problems below if you run into issues while following this guide.

<Accordions type="multiple">
  <Accordion title={<>A field you asked for with <code>_fields</code> is missing, with no error</>} value="fields-silently-dropped">
    Plytix drops some unrecognized field names rather than rejecting them, so a typo costs you the field and tells you nothing. Compare the name against one full, unfiltered product response, which is the authoritative list of what a product actually carries. Reading a single product once before you build the export list is the cheapest way to avoid this across a long run.
  </Accordion>
  <Accordion title={<><code>_fields=category_ids</code> returns 400 instead of the field</>} value="fields-ids-hidden">
    Any field ending in `_ids` is hidden from API responses, so this returns a `HiddenFieldError`. That's deliberate: Plytix doesn't expose the denormalized ID arrays behind its relationships. Ask for the expanded plural form instead, so `categories` rather than `category_ids`, and `assets` rather than `asset_ids`. The expanded form returns the full objects and includes the IDs you were after anyway.
  </Accordion>
  <Accordion title={<><code>_fields</code> doesn't narrow a single-product lookup</>} value="fields-single-product">
    `_fields` only applies to the search endpoint. `GET /products/{id}` always returns the complete product whatever you pass, so a sparse-field read has to go through `GET /products` with a filter that matches the one product you want.
  </Accordion>
</Accordions>
