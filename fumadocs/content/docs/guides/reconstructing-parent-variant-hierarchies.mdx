Build a parent and variant hierarchy, the way an ERP or marketplace needs it, using `parent_id` and `product_family_id`, and read its levels and structure back. Creating a product family, adding attributes to it, and assigning products into it all work through the V3 API with a bearer token. Inheritance between levels is an account-level feature that isn't enabled on every account, so ask your Plytix contact whether your account has it before you build against it.

## Prerequisites

Before you start, make sure you have the following:

- A bearer token. See [Authentication](/docs/reference/v3/authentication), or the [Quickstart](/docs/guides/quickstart) for a first walkthrough.
- An existing product family in your account. If you're not sure whether one exists, step 1 shows you how to check.

## Build and read the hierarchy

Follow the steps below to find or create a family, add a parent and its variants, and read the structure back.

1. **List the product families already in your account.**

   ```bash
   curl "https://pim.plytix.com/api/v3/product-families" \
     -H "Authorization: Bearer <access_token>"
   ```

   Each family includes `total_products`, `total_attributes`, and `total_models`, so you can confirm a family actually has data before building against it.

   To create one instead, `POST` a name:

   ```bash
   curl -X POST "https://pim.plytix.com/api/v3/product-families" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"name": "Backpacks"}'
   ```

   A family create also accepts `attributes`, `parent_attributes`, and `variant_attributes`, and the last two depend on inheritance being enabled on your account. Add attributes to it with `POST /api/v3/product-families/<family_id>/attributes`, sending `{"attribute_id": "<attribute_id>"}` for each one. A family's own `PATCH` accepts `name` only, because changing its attribute membership propagates across every product in the family.

2. **Create the parent product, assigned to that family.**

   ```bash
   curl -X POST "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"sku": "PARENT-001", "product_family_id": "<family_id>"}'
   ```

   A successful create returns `201` with the product itself, not only its ID, leaving out any field you didn't set. Note the `product_level: 0` in that response: putting a product in a family doesn't make it a parent. It becomes one in step 3, when a variant points at it.

3. **Create a variant, referencing the parent.**

   ```bash
   curl -X POST "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"sku": "VARIANT-001", "parent_id": "<parent_id>"}'
   ```

   A variant takes its family from its parent, so you can leave `product_family_id` out. If you do send it, it has to match the parent's: a different family is rejected with `422` and the generic message `"product data validation failed"`, which names no field, so it's worth recognizing.

4. **Read the parent back and confirm the hierarchy updated.**

   ```bash
   curl "https://pim.plytix.com/api/v3/products/<parent_id>" \
     -H "Authorization: Bearer <access_token>"
   ```

   Once a product has at least one variant, its `product_level` changes from `0` to `1`, and `num_variations` increments by one for each variant. The variant itself reads back at `product_level: 2`.

5. **Read the family's structure for a full picture.**

   ```bash
   curl "https://pim.plytix.com/api/v3/product-family-models/<family_id>" \
     -H "Authorization: Bearer <access_token>"
   ```

   A family model includes `parent_attribute_labels`, `variant_attribute_labels`, and `no_level_attribute_labels`, the arrays that define which attributes apply at each level of the hierarchy. These models are read-only.

   Which level an attribute sits at is what drives inheritance, and you change it with `PATCH /api/v3/product-families/<family_id>/attributes/<attribute_id>`, sending a new `level`. On accounts without the inheritance feature this returns `403` with `"Automatic inheritance is not available for this account"`, which is an account-level setting rather than anything wrong with your request.

## Read which values a variant overrides

{/* FLAG (open):
  This behavior is unverified. Inheritance is gated on the development account used for testing, so `overwritten_attributes` couldn't be tested, and the spec describes it only as "Overwritten attribute names". Confirm with Plytix before relying on it.

When inheritance is enabled and a variant overrides a value it would otherwise inherit, Plytix records that attribute's name in the variant's `overwritten_attributes` array. Read that field to see which values a specific variant customized and which it's still taking from its parent.
