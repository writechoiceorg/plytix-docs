Keep product data consistent between your ERP and Plytix by reading changes from Plytix on a schedule and writing your own changes back through the same API. This guide covers both directions: pulling updates into your ERP, and pushing stock, price, or status changes back to Plytix. All requests use the V3 API with a bearer token. Read [Update and delete records](/docs/reference/v3/updates-and-deletes) before you write, because a `PATCH` that names the `attributes` map replaces the whole map.

## Prerequisites

Before you start, make sure you have the following:

- A Plytix account with API credentials (an `api_key` and `api_password` from **Account Administration > API**).
- A way to exchange those credentials for a bearer token. See [Authentication](/docs/reference/v3/authentication), or the [Quickstart](/docs/guides/quickstart) for a first walkthrough.
- A field in your ERP to store each product's Plytix product ID, so you can address a product directly instead of searching by SKU on every call.

## Keep both systems in sync

Follow the steps below to authenticate, read changes from Plytix, push your own updates back, and confirm they were applied.

1. **Get an access token.**

   Exchange your `api_key` and `api_password` for a bearer token, as described in [Authentication](/docs/reference/v3/authentication). The token expires after 15 minutes, so request a new one when a call returns `401`.

2. **Resolve a product's Plytix ID from its SKU, the first time you see that SKU.**

   ```bash
   curl -G "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     --data-urlencode "sku=BAG-10157" \
     --data-urlencode "_fields=id"
   ```

   Storing the returned `id` alongside the SKU in your ERP is optional, because the SKU also works as the identifier in `GET /products/<identifier>`. It does make later calls steadier and faster, since they skip this lookup.

3. **Read the current product state.**

   ```bash
   curl "https://pim.plytix.com/api/v3/products/<product_id>" \
     -H "Authorization: Bearer <access_token>"
   ```

   The response includes `attributes`, `categories`, and `thumbnail_id`, along with a `product_relationships` field for any configured relationships.

4. **Find what changed since your last sync.**

   ```bash
   curl -G "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     --data-urlencode "modified[gt]=2026-09-01" \
     --data-urlencode "_fields=id" \
     --data-urlencode "_fields=sku"
   ```

   `modified` is the last-modification timestamp, so this catches edits as well as new products. Filtering on `created` returns only products added since the cutoff and misses every update, which is rarely what a sync wants. Store the timestamp of each successful sync and reuse it as the next run's filter value. Search results are paged, with a default page size of 25. See [Pagination](/docs/reference/v3/pagination) for how to read every page.

   {/* FLAG (open):
     Filtering on `created` is confirmed in testing. Filtering on `modified[gt]`, and whether `modified` advances after an attribute `PATCH`, hasn't been tested yet. Verify both on your account before you rely on this step.
   */}

5. **Push an attribute change back to Plytix.**

   Address the attribute directly by name and send its new value on its own. The body is the bare value, not an object:

   ```bash
   curl -X PATCH "https://pim.plytix.com/api/v3/products/<product_id>/attributes/price" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '34.99'
   ```

   This changes only the attribute you name and leaves every other attribute untouched, which makes it the right call for stock and price updates. Repeat it once per attribute you need to change.

   <Callout type="error" title="Don't send a partial attributes map to the product itself">
     `PATCH /products/<product_id>` with `{"attributes": {"price": 34.99}}` looks equivalent, but it isn't: naming `attributes` on the product replaces the entire map, and every attribute missing from your payload is deleted from the product. If you use that form, read the current `attributes` first, merge your change into the full map, and send the result back. Top-level fields such as `label` and `status` are safe to send on their own, and are left alone when omitted.
   </Callout>

   Either way, a successful `PATCH` returns `204` with an empty body, so confirm the result with a read-back (step 7) rather than parsing the response.

   See [Update and delete records](/docs/reference/v3/updates-and-deletes) for what each write returns and what DELETE removes.

6. **Create a product your ERP has that Plytix doesn't have yet.**

   ```bash
   curl -X POST "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"sku": "NEW-SKU-001", "label": "New Product"}'
   ```

   `sku` is the only required field. A successful create returns `201` with the product itself, not only its ID, so you can store the new `id` straight from the response without a follow-up read. Fields you didn't set are left out rather than returned empty.

   One shape difference to code around: on a create, `data` is a single object. On a search it's an array. Reusing one response parser across both will bite you.

   The request accepts and rejects these fields:

   | Fields | Result |
   |---|---|
   | `label`, `gtin`, `status`, `attributes`, `thumbnail_id`, `product_family_id`, `parent_id` | Accepted in the same request. |
   | `category_ids`, `static_list_ids`, `channel_ids`, `ecatalog_ids`, `product_data_sheet_ids` | Rejected with `422` and `"Extra inputs are not permitted"`, on create and on `PATCH` alike. |

   Categories are attached afterwards with `POST /products/<product_id>/categories`, sending `{"id": "<category_id>"}`. See [Safely remove categories, assets, or relationships](/docs/guides/safely-removing-categories-assets-or-relationships) for the full link and unlink pattern.

7. **Confirm the write took effect.**

   ```bash
   curl "https://pim.plytix.com/api/v3/products/<product_id>" \
     -H "Authorization: Bearer <access_token>"
   ```

   Because `PATCH` returns no body, this read-back is the only way to verify an update. Compare the fields you sent against the response, and check that the attributes you meant to keep are still there.

## Troubleshooting

Check the problems below if you run into issues while following this guide.

<Accordions type="multiple">
  <Accordion title={<><code>POST /products</code> returns 409 Conflict</>} value="post-products-409">
    If the response is `409` with an `AlreadyExists` error and the description `"product data validation failed"`, the SKU already exists in this account. The error doesn't name the field. Look it up with a search instead of creating it again, and check for an existing SKU before every create, using the lookup in step 2.
  </Accordion>
  <Accordion title={<><code>GET /products/&lt;identifier&gt;</code> returns 404</>} value="get-products-404">
    If the request returns `404` instead of the product, nothing in this account matches that identifier. Both the Plytix product ID and the SKU work in this position, but a SKU containing characters with special meaning in a URL has to be encoded first.

    To avoid SKU formatting issues altogether, store each product's Plytix ID in your ERP (step 2) so lookups don't depend on it.
  </Accordion>
  <Accordion title="Sending an empty string or empty list doesn't clear a field" value="empty-value-stored">
    Sending an empty string or an empty list stores that empty value instead of clearing the field. See [Update and delete records](/docs/reference/v3/updates-and-deletes) for what each write returns and what `DELETE` removes.
  </Accordion>
  <Accordion title="Attributes you didn't touch disappear after a sync run" value="attributes-disappear">
    A `PATCH` that names `attributes` replaces the whole map, so every attribute missing from your payload is removed. Read the product's current attributes, merge your change into them, and send the result.

    To avoid this entirely, address each attribute at its own path instead, as shown in step 5. `PATCH /products/<product_id>/attributes/<name>` changes only the attribute you name and is the safer default for a sync loop.
  </Accordion>
</Accordions>
