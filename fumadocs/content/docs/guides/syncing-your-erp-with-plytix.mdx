title: Sync your ERP with Plytix
description: Read product data from Plytix, detect what changed, and push stock, price, and status updates back so your ERP and Plytix stay in sync.
---

import { DocumentEditRegular, GaugeRegular } from '@/components/icons';

Keep product data consistent between your ERP and Plytix with a recurring sync: an initial import that reads the whole catalog once, then scheduled runs that read only what changed in Plytix and write your ERP's changes back. This guide covers both directions, how archives and deletions travel, and how to recover when a run fails partway. All requests use the V3 API at `https://pim.plytix.com/api/v3`. Searches return `data` as an array with a `pagination` object, single-product reads and creates return `data` as one object, and a successful `PATCH` returns `204` with no body. Read [Update and delete records](/reference/v3/updates-and-deletes) before you write, because a `PATCH` that names the `attributes` map replaces the whole map.

## Prerequisites

Before you start, make sure you have the following:

- API access to your Plytix account. How you get a token depends on the API version, as described in the first step of [Run the initial import](#run-the-initial-import).
- A custom attribute in Plytix for every ERP-owned field you sync, with a type that fits the data. This guide's examples use `price`, a decimal attribute, and `stock`, an integer attribute. Replace them with the attribute names in your account, which you can list with `GET /api/v3/product-attributes`.
- A place in your ERP to store the sync checkpoint, and optionally each product's Plytix `id`.

## Decide who owns each field

Give every synced field exactly one owner, and write it only in the owner's direction. A field that both systems write can bounce between them on every run. The split below is an example:

| Field | Owner | Direction |
|---|---|---|
| `label`, `status`, and descriptive attributes | Plytix | Plytix to ERP |
| `price` and `stock` | ERP | ERP to Plytix |
| `sku` | Both, as the shared key | Set once when the product is created, never changed by the sync |

One owner per field isn't enough on its own to stop loops. Your own writes can change a product's `modified` timestamp, so the next pull returns the products you updated. Compare values before you write in either direction, and skip the write when nothing differs.

## Run the initial import

Follow the steps below to authenticate and load every product into your ERP once, before the first scheduled run.

1. **Get an access token.**

   How you get a token depends on the API version. V1/V2 exchange your API Key and password for a bearer token, as described in [Authentication](/reference/v1-v2/token-authentication). V3 is moving to a new token-based authentication model whose details aren't published yet; see [Authentication and base URLs](/docs/guides/migrating-to-v3/authentication-and-base-urls). Whichever you use, request a new token when a call returns `401`. The examples below send the token as `Authorization: Bearer <access_token>`.

2. **Record the run boundary.**

   Before the first request, save the current time in UTC as a full timestamp, such as `2026-10-14T09:00:00Z`. This is the import's upper boundary, and it becomes the first checkpoint once the import finishes.

3. **Read every product with the fields your ERP needs.**

   ```bash
   curl -G "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     --data-urlencode "_fields=id" \
     --data-urlencode "_fields=sku" \
     --data-urlencode "_fields=label" \
     --data-urlencode "_fields=status" \
     --data-urlencode "_fields=attributes" \
     --data-urlencode "_fields=modified" \
     --data-urlencode "_page_size=100"
   ```

   Follow `pagination.next_page` until it's absent, as described in [Export your full catalog](/docs/guides/exporting-your-full-catalog). Relations such as `categories` and `product_relationships` are returned only when you name them, so add `_fields=categories` or `_fields=product_relationships` if your ERP needs them.

4. **Write each product into your ERP, keyed by SKU.**

   The SKU is enough to address a product: V3 accepts it as `{identifier}` in a path, URL-encoded. Storing the Plytix `id` as well is optional. It gives you a stable identifier that needs no encoding.

5. **Save the checkpoint.**

   After every page and every product is written, save the boundary from step 2 as the checkpoint. If the import stops partway, don't save it. Rerun the import instead.

## Pull changes from Plytix

Follow the steps below on each scheduled run to read the products that changed since the checkpoint and apply them in your ERP.

1. **Define the run's window.**

   Record the current UTC time as this run's boundary. The window starts at the saved checkpoint minus an overlap, for example five minutes, and ends at the boundary. The overlap re-reads a few products from the previous run, so a change written close to the last boundary isn't missed.

2. **Read the products modified inside the window, with the fields you apply.**

   ```bash
   curl -G "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     --data-urlencode "modified[gte]=2026-10-14T08:55:00Z" \
     --data-urlencode "modified[lt]=2026-10-14T10:00:00Z" \
     --data-urlencode "_fields=id" \
     --data-urlencode "_fields=sku" \
     --data-urlencode "_fields=status" \
     --data-urlencode "_fields=attributes" \
     --data-urlencode "_fields=modified" \
     --data-urlencode "_page_size=100"
   ```

   `modified` is the last-modification timestamp, so this returns edits as well as new products. Filtering on `created` instead returns only products added in the window. Read every page. Each page runs the query again, so a product edited while you're paging moves out of the window and can shift the pages after it. See [Search and pagination](/docs/guides/migrating-to-v3/searching-and-pagination) for that risk, and [Reconcile on a slower schedule](#reconcile-on-a-slower-schedule) for the safety net.

   {/* FLAG (open):
     Retested 2026-10-15 on the development account (FB-027): `modified[gte]` and `modified[lt]` combine in one request, full UTC timestamps, fractional seconds, and offsets are all accepted, `modified` advances after a single-attribute `PATCH` and after archiving, and archived products stay in the results with `status: Archived`. An invalid date returns `200` with an empty list instead of an error, so validate timestamps before sending. Still open: whether any call lists products deleted since a given time.
   */}

3. **Skip what you've already applied.**

   Deduplicate the products by `id`, because the overlap returns some products twice across runs. For each product, compare every Plytix-owned field with the value in your ERP and keep only the fields that differ.

4. **Apply the changes in your ERP.**

   Write only the Plytix-owned fields that differ. Handle products whose `status` is `Archived` as described in [Propagate archives and deletions](#propagate-archives-and-deletions).

5. **Advance the checkpoint.**

   Only after every page and every product in the window succeeds, save this run's boundary as the new checkpoint. If anything fails, keep the old checkpoint. The next run reads the same window again, and step 3 makes the repeat safe.

## Push ERP changes to Plytix

Follow the steps below to write ERP-owned fields back to Plytix and create the products Plytix doesn't have yet.

1. **Compare before you write.**

   For each ERP-owned field, compare the ERP value with the value Plytix returned in your last pull. Skip the write when they match, so your own updates don't come back as new changes.

2. **Update one attribute at a time.**

   ```bash
   curl -X PATCH "https://pim.plytix.com/api/v3/products/<product_id>/attributes/price" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '34.99'
   ```

   Address the attribute by name at its own path, and send the bare JSON value, not an object. This changes only the attribute you name. `<product_id>` can also be the product's SKU, URL-encoded. A `204` means the update succeeded. Read the product back only when your integration needs the resulting values.

   {/* FLAG (open):
     The bare-value body is confirmed live for a text attribute (a JSON string). A number, such as `34.99` on a decimal attribute, hasn't been tested on this path, and the OpenAPI declares no request body for it (FB-020).
   */}

   <Callout type="error" title="Don't send a partial attributes map to the product itself">
     `PATCH /products/<product_id>` with `{"attributes": {"price": 34.99}}` replaces the entire `attributes` map. In testing, every attribute missing from the payload was removed; see the before-and-after example in [Responses and updates](/docs/guides/migrating-to-v3/responses-and-updates#how-patch-treats-the-attributes-map). Top-level fields such as `label` and `status` are merged, so you can send them on their own. To change several attributes in one request, you have to read the current map, merge your changes, and send the whole map back. V3 has no conditional write, so a change another user makes between your read and your write is overwritten. In a sync loop, use the single-attribute path instead.
   </Callout>

3. **Create the products Plytix doesn't have yet.**

   ```bash
   curl -X POST "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"sku": "NEW-SKU-001", "label": "New Product"}'
   ```

   `sku` is the only required field. A successful create returns `201` with the created product, so you can store its `id` from the response. On a create, `data` is a single object; on a search, it's an array, so don't reuse one parser for both. Don't rely on fields you didn't set being absent from the response, because they can also come back as `null`.

   The request accepts and rejects these fields:

   | Fields | Result |
   |---|---|
   | `label`, `gtin`, `status`, `attributes`, `thumbnail_id`, `product_family_id`, `parent_id` | Accepted in the same request. |
   | `category_ids`, `static_list_ids`, `channel_ids`, `ecatalog_ids`, `product_data_sheet_ids` | Rejected with `422` and `"Extra inputs are not permitted"`, on create and on `PATCH` alike. |

   Categories are attached afterwards with `POST /products/<product_id>/categories`, sending `{"id": "<category_id>"}`. See [Unlink categories, assets, or relationships](/docs/guides/safely-removing-categories-assets-or-relationships) for the full link and unlink pattern.

   Checking for the SKU before you create doesn't rule out a conflict, because another process can create the same SKU between your check and your `POST`. If the create returns `409`, search for the SKU, confirm it's the product you meant to create, and update it instead of repeating the `POST`.

## Propagate archives and deletions

Polling `modified` can't find deleted products, because a deleted product no longer appears in any search. Handle each case explicitly:

- **Archived in Plytix:** the pull returns the product with `status` set to `Archived`. Decide whether your ERP deactivates it or ignores it.
- **Deleted in Plytix:** a deleted product drops out of every search, so the scheduled pull never sees it. Find it with the reconciliation pass in [Reconcile on a slower schedule](#reconcile-on-a-slower-schedule).
- **Removed from your ERP:** either archive the product in Plytix with `PATCH /api/v3/products/<product_id>` and `{"status": "Archived"}`, which keeps its data, or delete it with `DELETE /api/v3/products/<product_id>`, which removes it.

### Reconcile on a slower schedule

A scheduled pull can miss a change, and it never shows a deletion. On a slower schedule, such as nightly, run a full pass that compares values as well as IDs. Follow the steps below to run it safely.

1. **Read the full catalog.** Run the product search with no `modified` filter, requesting `id` plus every field your ERP syncs, the same `_fields` as step 3 of [Run the initial import](#run-the-initial-import). Add `_sort_by=id` so the order is deterministic. Read every page. If any page fails, discard the pass and run it again later, rather than comparing a partial list.
2. **Compare values, not only IDs.** For each product that both systems hold, compare the synced values with your ERP's copy. A difference is a change that a scheduled run missed. Apply it the same way a scheduled run would.
3. **Treat a missing product as a candidate, not a deletion.** A product your ERP holds that the pass didn't return isn't proven deleted. It may sit outside the pass's scope, for example because of a filter in your search or the permissions of your API credentials, or the catalog may have shifted while you paged. Request it directly with `GET /api/v3/products/<product_id>`. Only a `404` confirms that it's gone. Any other error leaves it as a candidate for the next pass.
4. **Act only on confirmed deletions.** Deactivate or delete the product in your ERP only after step 3 confirms it.

## Recover from failed runs

Design each run so you can repeat it safely. Plan for these failures:

- **Rate limits:** your access token carries your account's limits, as described in [Rate limits](/reference/v3/rate-limits). Pace requests under them. If a request returns `429`, wait before retrying and slow the whole run down. The limits haven't been observed being enforced in testing, so the `429` response hasn't been captured yet.
- **Transient failures:** retry timeouts and `5xx` responses a few times, with an increasing delay between attempts. Don't retry `4xx` responses such as `422` unchanged, because the request itself needs fixing.
- **Retried writes:** a single-attribute `PATCH` is safe to repeat, because sending the same value twice leaves the same result. A `POST` isn't. Handle a `409` as described in step 3 of [Push ERP changes to Plytix](#push-erp-changes-to-plytix).
- **Partial runs:** because the checkpoint advances only after the whole window succeeds, a failed run is retried in full on the next schedule. Log the products that failed, so you can find the ones that fail on every run.
- **Expired tokens:** when a call returns `401`, get a new token and retry the request.

## Troubleshooting

Check the problems below if you run into issues while following this guide.

<Accordions type="multiple">
  <Accordion title={<><code>POST /products</code> returns 409 Conflict</>} value="post-products-409">
    If the response is `409` with an `AlreadyExists` error and the description `"product data validation failed"`, the SKU already exists in this account. The error doesn't name the field. Search for the SKU, confirm it's the same product, and update it instead of repeating the `POST`.
  </Accordion>
  <Accordion title={<><code>GET /products/&lt;identifier&gt;</code> returns 404</>} value="get-products-404">
    If the request returns `404` instead of the product, nothing in this account matches that identifier. Both the Plytix product ID and the SKU work in this position, but a SKU containing characters with special meaning in a URL has to be encoded first. Storing each product's Plytix `id` in your ERP avoids the encoding step.
  </Accordion>
  <Accordion title="The same products come back on every run" value="same-products-every-run">
    If each pull returns the products your previous run wrote to Plytix, your own writes are updating their `modified` timestamp. Compare values before you write, as described in [Decide who owns each field](#decide-who-owns-each-field), so an unchanged value is never sent.
  </Accordion>
  <Accordion title="An empty value you sent doesn't appear on the product" value="empty-value-stored">
    On the attribute types tested, sending `""`, `[]`, or `null` clears the value, so the attribute is absent from the product afterward rather than stored as empty. A media attribute rejects `""`; clear it with `DELETE` on the attribute's path instead. See [Responses and updates](/docs/guides/migrating-to-v3/responses-and-updates#empty-values-null-and-deletion) for the tested cases by attribute type.
  </Accordion>
  <Accordion title="Attributes you didn't touch disappear after a sync run" value="attributes-disappear">
    A `PATCH` on the product that names `attributes` replaces the whole map, so every attribute missing from your payload is removed. Send the changed attributes as a partial map to `PATCH /products/<product_id>/attributes`, which merges them, or address each attribute at its own path, as shown in step 2 of [Push ERP changes to Plytix](#push-erp-changes-to-plytix). `PATCH /products/<product_id>/attributes/<name>` changes only the attribute you name.
  </Accordion>
</Accordions>
