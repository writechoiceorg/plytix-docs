Keep product data consistent between your ERP and Plytix by reading changes from Plytix on a schedule and writing your own changes back through the same API. This guide covers both directions: pulling updates into your ERP, and pushing stock, price, or status changes back to Plytix.

## Prerequisites

Before you start, make sure you have the following:

- A Plytix account with API credentials (an `api_key` and `api_password` from **Account Administration > API**).
- A way to exchange those credentials for a bearer token. See [Authentication](/docs/reference/v3/authentication), or the [Quickstart](/docs/guides/quickstart) for a first walkthrough.
- A field in your ERP to store each product's Plytix product ID, so you can address a product directly instead of searching by SKU on every call.

## Sync your ERP

Follow the steps below to authenticate, read changes from Plytix, push your own updates back, and confirm they were applied.

1. **Get an access token.**

   Exchange your `api_key` and `api_password` for a bearer token, as described in [Authentication](/docs/reference/v3/authentication). The token expires after 15 minutes, so request a new one when a call returns `401`.

2. **Resolve a product's Plytix ID from its SKU, the first time you see that SKU.**

   ```bash
   curl -G "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     --data-urlencode "sku=BAG-10157" \
     --data-urlencode "_fields=id"
   ```

   Store the returned `id` alongside the SKU in your ERP so every later call can skip this lookup.

3. **Read the current product state.**

   ```bash
   curl "https://pim.plytix.com/api/v3/products/<product_id>" \
     -H "Authorization: Bearer <access_token>"
   ```

   The response includes `attributes`, `categories`, and `thumbnail_id`, along with a `product_relationships` field for any configured relationships.

4. **Find what changed since your last sync.**

   ```bash
   curl -G "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     --data-urlencode "modified[gt]=2026-09-01" \
     --data-urlencode "_fields=id" \
     --data-urlencode "_fields=sku"
   ```

   `modified` is the last-modification timestamp, so this catches edits as well as new products. Filtering on `created` returns only products added since the cutoff and misses every update, which is rarely what a sync wants. Store the timestamp of each successful sync and reuse it as the next run's filter value.

5. **Push an attribute change back to Plytix.**

   Address the attribute directly by name and send its new value on its own. The body is the bare value, not an object:

   ```bash
   curl -X PATCH "https://pim.plytix.com/api/v3/products/<product_id>/attributes/price" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '34.99'
   ```

   This changes only the attribute you name and leaves every other attribute untouched, which makes it the right call for stock and price updates. Repeat it once per attribute you need to change.

   <Callout type="error" title="Don't send a partial attributes map to the product itself">
     `PATCH /products/<product_id>` with `{"attributes": {"price": 34.99}}` looks equivalent, but it isn't: naming `attributes` on the product replaces the entire map, and every attribute missing from your payload is deleted from the product. If you use that form, read the current `attributes` first, merge your change into the full map, and send the result back. Top-level fields such as `label` and `status` are safe to send on their own, and are left alone when omitted.
   </Callout>

   Either way, a successful `PATCH` returns `204` with an empty body, so confirm the result with a read-back (step 7) rather than parsing the response.

   Sending an empty string or an empty list stores that empty value instead of clearing the field. See [Working with Updates and Deletes](/docs/reference/v3/updates-and-deletes) for what each write returns and what DELETE removes.

6. **Create a product your ERP has that Plytix doesn't have yet.**

   ```bash
   curl -X POST "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"sku": "NEW-SKU-001", "label": "New Product"}'
   ```

   `sku` is the only required field. Everything else, including `attributes` and `category_ids`, can follow in the same request or a later `PATCH`. A successful create returns `201` with the full created product, not only its ID, even though some Plytix API documentation describes `POST` as returning only an ID.

7. **Confirm the write took effect.**

   ```bash
   curl "https://pim.plytix.com/api/v3/products/<product_id>" \
     -H "Authorization: Bearer <access_token>"
   ```

   Because `PATCH` returns no body, this read-back is the only way to verify an update. Compare the fields you sent against the response, and check that the attributes you meant to keep are still there.

## Troubleshooting

Check the problems below if you run into issues while following this guide.

<Accordions type="multiple">
  <Accordion title={<><code>POST /products</code> returns 409 Conflict</>} value="post-products-409">
    If the response includes `"A product with the same name already exists"`-style text, the SKU already exists in this account. Look it up with a search instead of creating it again, and check for an existing SKU before every create, using the lookup in step 2.
  </Accordion>
  <Accordion title={<><code>GET /products/&lt;identifier&gt;</code> returns 404</>} value="get-products-404">
    If the request returns `404` instead of the product, nothing in this account matches that identifier. Both the Plytix product ID and the SKU work in this position, but a SKU containing characters with special meaning in a URL has to be encoded first.

    To avoid SKU formatting issues altogether, store each product's Plytix ID in your ERP (step 2) so lookups don't depend on it.
  </Accordion>
  <Accordion title="Attributes you didn't touch disappear after a sync run" value="attributes-disappear">
    A `PATCH` that names `attributes` replaces the whole map, so every attribute missing from your payload is removed. Read the product's current attributes, merge your change into them, and send the result, as shown in step 5.

    To avoid this, never build a `PATCH` body with only the changed attribute in it.
  </Accordion>
</Accordions>
