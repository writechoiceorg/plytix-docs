Authentication is the part of a migration that doesn't change. V1/V2 and V3 authenticate against the same service and accept the same token. This page records what you send with every request. It's part of the reference set for [Migrating to V3](/docs/guides/migrating-to-v3).

## Base URLs and paths

| | V1/V2 | V3 |
|---|---|---|
| Base URL | `https://pim.plytix.com` | `https://pim.plytix.com` |
| Path prefix | `/api/v1`, `/api/v2` | `/api/v3` |
| Auth service | `https://auth.plytix.com` | Same |
| Token request | `POST /auth/api/get-token` with `api_key` and `api_password` | Same |
| Request header | `Authorization: Bearer <token>` | Same |

{/* FLAG (open):
  The V3 base URL `https://pim.plytix.com/api/v3` and the claim that one token works against both versions are not fully confirmed. Live testing confirmed V3 only on `pim.dev.plytix.com` with a dev token. On the production host, V3 returned `401` to a dev token. Re-test with a production credential before relying on this table for V3.
*/}

Credentials, their roles, and token-refresh logic carry over unchanged. An integration that keeps some calls on V1 doesn't need a second auth flow.

## Token flow

Post your API Key and password to the auth service, and send the token back as a bearer header on every call. Nothing in a migration requires new credentials, a second token, or a change to your refresh logic. See [Authentication](/docs/reference/v3/authentication) for the token request, and [Quickstart](/docs/guides/quickstart) for the full flow, including how long a token lasts.
