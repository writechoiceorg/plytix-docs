V1/V2 share one authentication flow, and V3 uses access tokens you create in your account settings. This page lists the base URLs, path prefixes, and authentication details for each. It's part of the reference set for [Migration overview](/docs/guides/migrating-to-v3).

## V1/V2 base URL and authentication

V1/V2 share one authentication flow. You exchange your API credentials for a bearer token, then send that token with every request to either version.

| Item | Value |
|---|---|
| API base URL | `https://pim.plytix.com` |
| API path prefixes | `/api/v1`, `/api/v2` |
| Token endpoint | `POST https://auth.plytix.com/auth/api/get-token` |
| Credentials in the token request | `api_key` and `api_password`, in a JSON body |
| Header on every API request | `Authorization: Bearer <token>` |

### API credentials and bearer tokens

Your API credentials and your bearer token do different jobs. The credentials identify you once, at the token endpoint. The token authenticates every API request after that.

| | API credentials | Bearer token |
|---|---|---|
| What it is | Your API Key and password | A short-lived access token, returned as `access_token` |
| Where it comes from | An account administrator issues them from the **API** tab in the account's Admin section | The token endpoint, in exchange for your credentials |
| Where you send it | Only in the body of the token request | In the `Authorization` header of every V1/V2 request |

A token expires after 15 minutes. When it expires, or the API can't verify it, requests return `401`, and you request a new token with the same credentials. See [Authentication](/reference/v1-v2/token-authentication) for the full token request, response, and errors.

## V3 base URL and authentication

V3 runs on the same base URL as V1/V2, under its own path prefix, but it authenticates differently. There's no token request: you create an access token in your account settings and send it directly.

| Item | Value |
|---|---|
| API base URL | `https://pim.plytix.com` |
| API path prefix | `/api/v3` |
| Where the token comes from | The **API v3** tab in your account settings, available once the V3 beta is enabled for your account |
| Header on every API request | `Authorization: Bearer <access_token>` |
| Token lifetime | Until the expiration date you choose when you create it, unless you rotate or revoke it first |

### What changes from V1/V2

These are the differences that affect integration code moving from V1/V2 to V3:

| | V1/V2 | V3 |
|---|---|---|
| How you get a token | `POST` your API Key and password to the token endpoint | Create it in the **API v3** tab, then copy it |
| Lifetime | 15 minutes | 7 days, 1 month, 1 year, or a custom date |
| Access | The role assigned to the API Key | Per-resource permissions you set on the token, within your own user role |
| When it stops working | It expires, and you request a new one with the same credentials | It expires, or you rotate or revoke it, and you update your integration with a new value |

A V3 access token works only with V3, so an integration that keeps some calls on V1/V2 needs both. Because a V3 token doesn't come from a request, your integration can't fetch a new one on `401`. Store the token where you can replace it without a deploy, such as a secret manager, and replace it before its expiration date. See [Authentication](/reference/v3/authentication) for creating, rotating, and revoking tokens.
