This page maps the V1/V2 endpoints most integrations use to their V3 equivalents, one resource at a time, and ends with the link and unlink endpoints that replaced V1's array fields. Where an operation has no V3 equivalent, the table says so rather than guessing at the nearest match; [Not migrated and new in V3](/docs/guides/migrating-to-v3/not-migrated-and-new-in-v3) collects those in one place. It's part of the reference set for [Migrating to V3](/docs/guides/migrating-to-v3).

## Products

| V1/V2 | V3 |
|---|---|
| `POST /api/v1/products` | `POST /api/v3/products` |
| `POST /api/v1/products/search` | `GET /api/v3/products` |
| `GET /api/v1/products/{product_id}` | `GET /api/v3/products/{identifier}` |
| `PATCH /api/v1/products/{product_id}` | `PATCH /api/v3/products/{identifier}` |
| `DELETE /api/v1/products/{product_id}` | `DELETE /api/v3/products/{identifier}` |
| `GET /api/v1/products/{product_id}/assets` | `GET /api/v3/products/{identifier}/assets`, or `GET /api/v3/products?_fields=assets` |
| `POST /api/v1/products/{product_id}/assets` | No equivalent. Stays on V1 |
| `DELETE /api/v1/products/{product_id}/assets/{asset_id}` | No equivalent. Stays on V1 |
| `GET /api/v1/products/{product_id}/categories` | `GET /api/v3/products/{identifier}/categories`, or `GET /api/v3/products?_fields=categories` |
| `POST /api/v1/products/{product_id}/categories` | `POST /api/v3/products/{identifier}/categories` |
| `DELETE /api/v1/products/{product_id}/categories/{category_id}` | `DELETE /api/v3/products/{identifier}/categories/{id}` |
| `POST /api/v1/products/{product_id}/family` | `PATCH /api/v3/products/{identifier}` with `product_family_id` |

In V3, `{identifier}` accepts either the product ID or the SKU, URL-encoded.

For the two read rows above, you can use V3's per-relation subpath or request the relation as `_fields` on a search. Both return the related records.

## Variants

V3 has no variant endpoints. A variant is an ordinary product that names its parent, so creation and deletion go through the regular product endpoints.

| V1/V2 | V3 |
|---|---|
| `POST /api/v1/products/{parent_product_id}/variants` | `POST /api/v3/products` with `parent_id` and `product_family_id` |
| `GET /api/v1/products/{product_id}/variants` | `GET /api/v3/products?parent_id=<parent_id>` {/* [PENDING] */} |
| `DELETE /api/v1/products/{parent_product_id}/variant/{variant_id}` | `DELETE /api/v3/products/{identifier}` |
| `POST /api/v1/products/{parent_product_id}/variants/resync` | No equivalent. Stays on V1 |

A product's position in the hierarchy is reported by `product_level`: `0` SINGLE, `1` PARENT, `2` VARIANT, `3` SUB_VARIANT. A standalone product starts at `0` and becomes `1` as soon as another product references it through `parent_id`. See [Reconstruct parent/variant hierarchies](/docs/guides/reconstructing-parent-variant-hierarchies).

{/* FLAG (open):
  Listing a parent's variants with `?parent_id=<id>` is unconfirmed. It follows from `parent_id` being a real product field, but filtering on it was never tested, and [Reconstruct parent/variant hierarchies](/docs/guides/reconstructing-parent-variant-hierarchies) reads the hierarchy from the parent's own `num_variations` instead. Verify with `endpoint-tester` before publishing, or drop the row and point at the parent-read method.
*/}

## Product relationships

| V1/V2 | V3 |
|---|---|
| `POST /api/v1/products/{product_id}/relationships/{relationship_id}` | `POST /api/v3/products/{product_id}/relationships/{relationship_id}` |
| `PATCH /api/v1/products/{product_id}/relationships/{relationship_id}/product/{related_product_id}` | `PATCH /api/v3/products/{product_id}/relationships/{relationship_id}` |
| `POST /api/v1/products/{product_id}/relationships/{relationship_id}/unlink` | `DELETE /api/v3/products/{product_id}/relationships/{relationship_id}` |
| `DELETE /api/v2/products/{product_id}/relationships/{relationship_id}` | `DELETE /api/v3/products/{product_id}/relationships/{relationship_id}` |
| Not available | `GET` and `POST /api/v3/products/{product_id}/relationships` |
| Not available | `GET /api/v3/products/{product_id}/relationships/{relationship_id}/related-products` {/* [PENDING] */} |
| Not available | `GET /api/v3/product-relationships` |
| Not available | `GET /api/v3/related-products` |

<Callout type="warn" title="Always filter the account-wide relationship endpoints">
  `GET /api/v3/product-relationships`, `/related-products`, and `/family-attributes` return account-wide data when called with no filter. Always scope them by `product_id` or `account_id`.
</Callout>

{/* FLAG (open):
  `GET /products/{id}/relationships/{relationship_id}/related-products[/{related_product_id}]` is unconfirmed. It returned empty or `404` for a link confirmed to exist by three other means. Ask Plytix whether it is unfinished before documenting it as usable.
*/}

## Assets

| V1 | V3 |
|---|---|
| `POST /api/v1/assets` | `POST /api/v3/assets`, with `url` or `content` |
| `POST /api/v1/assets/search` | `GET /api/v3/assets` |
| `GET /api/v1/assets/{asset_id}` | `GET /api/v3/assets/{identifier}` |
| `PATCH /api/v1/assets/{asset_id}` | `PATCH /api/v3/assets/{identifier}`, with `filename` and `alt_text` only |
| `DELETE /api/v1/assets/{asset_id}` | `DELETE /api/v3/assets/{identifier}` |
| `PUT /api/v1/assets/{asset_id}/content` | No equivalent. Stays on V1 |

V3 accepts binary content only at creation. Replacing the content of an existing asset has no V3 path, and the V3 asset update schema carries only `filename` and `alt_text`.

| V1 | V3 |
|---|---|
| `POST /api/v1/product_families` | `POST /api/v3/product-families` |
| `POST /api/v1/product_families/search` | `GET /api/v3/product-families` |
| `GET /api/v1/product_families/{product_family_id}` | `GET /api/v3/product-families/{identifier}` |
| `PATCH /api/v1/product_families/{product_family_id}` | `PATCH /api/v3/product-families/{identifier}` |
| `DELETE /api/v1/product_families/{product_family_id}` | `DELETE /api/v3/product-families/{identifier}` |
| `GET /api/v1/product_families/{product_family_id}/attributes` | `GET /api/v3/product-families/{product_family_id}/attributes` |
| `GET /api/v1/product_families/{product_family_id}/all_attributes` | `GET /api/v3/family-attributes` |
| `POST /api/v1/product_families/{id}/attributes/link` | `POST /api/v3/product-families/{product_family_id}/attributes` |
| `POST /api/v1/product_families/{id}/attributes/unlink` | `DELETE /api/v3/product-families/{product_family_id}/attributes/{attribute_id}` |
| `POST /api/v1/product_families/{id}/attributes/edit` | `PATCH /api/v3/product-families/{product_family_id}/attributes/{attribute_id}` |

You can create a Product Family, link attributes to it, and rename it through the API in both versions. Changing an attribute link's `level` (inheritance between levels) returns `403` on accounts without automatic inheritance.

## Linking and unlinking

V1 links through dedicated subpaths. V3 originally accepted `category_ids` and `static_list_ids` arrays on create and update; those fields are no longer accepted, leaving the dedicated link and unlink endpoints as the only route.

| Link | V1 | V3 |
|---|---|---|
| Product to category | `POST /api/v1/products/{product_id}/categories` | `POST /api/v3/products/{identifier}/categories` |
| Product from category | `DELETE /api/v1/products/{product_id}/categories/{category_id}` | `DELETE /api/v3/products/{identifier}/categories/{id}` |
| Asset to category | Through `categories` on the asset | `POST /api/v3/assets/{identifier}/categories` |
| Asset from category | Through `categories` on the asset | `DELETE /api/v3/assets/{identifier}/categories/{id}` |
| Attribute to group | Include the attribute in `attribute_labels` when you create the group with `POST /api/v1/attribute-groups/product` | `POST /api/v3/product-attributes/{identifier}/groups` |
| Attribute from group | Not available | `DELETE /api/v3/product-attributes/{identifier}/groups/{id}` |
| Product to asset | `POST /api/v1/products/{product_id}/assets` | **No V3 equivalent.** Stays on V1 |
| Product from asset | `DELETE /api/v1/products/{product_id}/assets/{asset_id}` | **No V3 equivalent.** Stays on V1 |
| Product to family | `POST /api/v1/products/{product_id}/family` | `PATCH /api/v3/products/{identifier}` with `product_family_id` |

<Callout type="warn" title="The generic subpath DELETE is not an unlink">
  `DELETE /api/v3/products/{identifier}/{path}` doesn't remove a single linked record. A collection path such as `categories` returns `405`, and an unrecognized path returns `404`. Use the specific unlink endpoints above.
</Callout>
