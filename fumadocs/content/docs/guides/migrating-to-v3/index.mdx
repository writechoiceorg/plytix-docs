V3 reorganized the Plytix API rather than replicating it. Most of what a V1/V2 integration does moves across and gets better in the process, but a few operations have no V3 equivalent at all, so a working integration usually ends up calling both versions rather than cutting over wholesale.

This guide covers that split: what moves, what stays, and how to convert the parts that move. Your authentication doesn't change either way.

## Prerequisites

Before you start, you need:

- **A working V1/V2 integration**, and access to its source. This guide assumes you're changing existing code, not starting fresh.
- **A test account or a safe dataset.** Write behavior differs between versions in ways that are hard to spot until something is already deleted.
- **Your current API credentials.** They keep working, so you don't need new ones.

## Migrate your integration

1. **Work out what actually moves.**

   Start here rather than with the endpoint mapping. Three groups matter, and the middle one is the reason a cutover is rarely clean.

   **Move these to V3.** Everything in this group has a V3 equivalent, and V3 is the better place for it:

   | Operation | Why V3 |
   |---|---|
   | Searching and reading any resource | Richer operators, real `OR` grouping, field expansion in one call |
   | Create, update, and delete on products, assets, categories, asset categories, product attributes, attribute groups, families, and relationships | Consistent conventions across every resource |
   | Linking products to categories, assets to categories, and attributes to groups | Dedicated link and unlink endpoints, rather than rewriting an array |
   | Adding and removing product relationships | V3's `DELETE /products/{product_id}/relationships/{relationship_id}` is a scoped unlink; V1 needs a separate `/unlink` call |
   | Creating variants | `parent_id` and `product_family_id` on the product itself |

   **Keep these on V1/V2.** No V3 equivalent exists today, so these calls stay where they are:

   | Operation | V1 endpoint | Status in V3 |
   |---|---|---|
   | Replacing the binary content of an existing asset | `PUT /api/v1/assets/{asset_id}/content` | No equivalent. V3 accepts `url` or `content` only when the asset is created; its update schema carries only `filename` and `alt_text` |
   | Linking and unlinking assets on a product | `POST` and `DELETE /api/v1/products/{product_id}/assets` | No equivalent, and not supported. V3 has no product-to-asset link path and no `asset_ids` field on the product. `thumbnail_id` is the one exception, and it sets a single image |
   | Discovering the available filters for a resource | `GET /api/v1/filters/product`, `/filters/asset`, `/filters/relationships` | No equivalent. Build filters from `GET /api/v3/product-attributes` instead |
   | Resyncing variants against their parent | `POST /api/v1/products/{parent_product_id}/variants/resync` | No equivalent |
   | Reading a total result count | `total_count` on every V1 search response | No equivalent anywhere in V3. See step 6 |

   **These are gone from both.** Plan around them rather than migrating them:

   - **Bulk writes.** V3 has no bulk create, update, or delete endpoints. A Bulk API exists in V2, but it isn't available to every account; confirm access with your Plytix contact. See [Bulk operations for large catalogs](/docs/guides/bulk-operations-for-large-catalogs).
   - **API credential and membership management** (`POST /api/v1/accounts/api-credentials/search`, `/accounts/memberships/search`). Manage these in the Plytix dashboard. API Keys are under the **API** tab.

   <Callout type="info" title="Running both versions is the normal end state">
     Both versions take the same bearer token against the same auth service, so calling V1 for asset content and V3 for everything else needs no extra credentials and no second auth flow. Treat the mixed setup as the destination, not as an unfinished migration.
   </Callout>

2. **Keep your authentication as it is.**

   Both versions use the same auth service. You exchange your API Key and password once, then send the token as a bearer header. Your existing credentials, their roles, and your token-refresh logic all carry over. See [Authentication and base URLs](/docs/guides/migrating-to-v3/authentication-and-base-urls) for the shared base URLs, [Authentication](/docs/reference/v3/authentication) for the token request, and [Quickstart](/docs/guides/quickstart) for the full flow.

3. **Convert your searches from a POST body to a GET query.**

   This is the largest change in the parts that do move. In V1, a search is a POST with a JSON body. In V3, it's a GET with query parameters, and the filters move into the URL.

   <Tabs items={['V1', 'V3']}>
     <Tab value="V1">
       ```bash
       curl --request POST \
         --url https://pim.plytix.com/api/v1/products/search \
         --header 'Authorization: Bearer <token>' \
         --header 'Content-Type: application/json' \
         --data '{
           "filters": [
             [
               {"field": "status", "operator": "eq", "value": "Draft"},
               {"field": "categories", "operator": "in", "value": ["5c4ed7f62f0985001c233274"]}
             ]
           ],
           "attributes": ["label", "status", "categories"],
           "pagination": {"order": "sku", "page": 1, "page_size": 25}
         }'
       ```
     </Tab>
     <Tab value="V3">
       ```bash
       curl --globoff --request GET \
         --url 'https://pim.plytix.com/api/v3/products?status=Draft&categories[in]=5c4ed7f62f0985001c233274&_fields=label&_fields=status&_fields=categories&_sort_by=sku&_page=1&_page_size=25' \
         --header 'Authorization: Bearer <token>'
       ```
     </Tab>
   </Tabs>

   Three parts of the body become three kinds of parameter:

   | V1 body key | V3 equivalent |
   |---|---|
   | `filters` | Query parameters in bracket syntax, such as `status=Draft` or `categories[in]=<id>` |
   | `attributes` | `_fields=<name>`, repeated once per field |
   | `pagination` | `_page`, `_page_size`, and `_sort_by` |

   The operators change shape but not meaning. `{"operator": "eq"}` becomes `field=value` or `field[eq]=value`, `!exists` becomes `field[!exists]=true`, `in` becomes `field[in]=value` repeated per value, and the comparison operators become `field[gt]`, `field[gte]`, `field[lt]`, and `field[lte]`.

   Boolean grouping changes too. In V1, filters nest as arrays: items inside one array combine with AND, and the outer arrays combine with OR. In V3, `&` is AND, and OR uses an indexed prefix:

   ```text
   _or[0]status=Draft&_or[0]status=Review
   ```

   Custom attributes are addressed directly rather than through a field name string: `attributes.name[eq]=value`. [Filter operators](/docs/guides/migrating-to-v3/filter-operators) carries the full operator mapping.

   {/* FLAG (open):
     The V1 grouping semantics (AND within an inner array, OR between outer arrays) are unconfirmed. `openapi_pimv1.json` was converted from a Postman collection, and its own description says the shapes were inferred from saved examples rather than verified against the live API. Confirm with `endpoint-tester` before publishing. The V3 side is confirmed.
   */}

4. **Update your endpoint paths.**

   V3 names resources consistently: plural, kebab-case, and resource-first, rather than a type appended to a generic path. A few common moves:

   | V1 | V3 |
   |---|---|
   | `/api/v1/attributes/product` | `/api/v3/product-attributes` |
   | `/api/v1/attribute-groups/product` | `/api/v3/product-attribute-groups` |
   | `/api/v1/categories/product` | `/api/v3/product-categories` |
   | `/api/v1/categories/file` | `/api/v3/asset-categories` |
   | `/api/v1/product_families` | `/api/v3/product-families` |

   Two changes are worth calling out beyond the renaming:

   - **Products accept more than one identifier.** In V3, both the product ID and the SKU work in the path, as long as the SKU is URL-encoded. That removes a lookup step for integrations keyed on SKU.
   - **Related data comes back with the record.** Where V1 has a separate call for each relation, V3 returns them through field selection on a search: `GET /api/v3/products?sku=<sku>&_fields=categories&_fields=assets`. The per-relation subpaths, such as `GET /api/v3/products/{identifier}/categories`, return the same data one relation at a time.

   See [Endpoint mapping](/docs/guides/migrating-to-v3/endpoint-mapping) for the complete mapping.

5. **Replace array-field linking with the link and unlink endpoints.**

   If you translated a V1 link operation into a V3 `PATCH` that sends a `category_ids` or `static_list_ids` array, that approach no longer works. Those fields are not accepted on product or asset writes, and linking has its own endpoints:

   | To do this | Call |
   |---|---|
   | Link a category to a product | `POST /api/v3/products/{identifier}/categories` |
   | Unlink it | `DELETE /api/v3/products/{identifier}/categories/{id}` |
   | Link a category to an asset | `POST /api/v3/assets/{identifier}/categories` |
   | Unlink it | `DELETE /api/v3/assets/{identifier}/categories/{id}` |
   | Link an attribute to a group | `POST /api/v3/product-attributes/{identifier}/groups` |
   | Unlink it | `DELETE /api/v3/product-attributes/{identifier}/groups/{id}` |

   Don't use the generic `DELETE /products/{identifier}/{path}` form to unlink. It isn't a scoped removal: an unrecognized path returns `404`, and a collection path such as `categories` returns `405`.

6. **Rework anything that reads a result count.**

   V1 returned `total_count` on every search. V3 has no equivalent: the pagination block carries no counts, and there is no parameter that adds one. Requesting `_total_count` or `_filtered_count` returns `400 InvalidFieldError`.

   Anything in your integration that reads a total has to be reworked to page to the end and tally: a progress bar, a "showing N of M" label, a pre-sized buffer, a sanity check that compares an expected count against a returned one. V3 also paginates by returning the next page's URL rather than a page number to increment, so the loop follows `next_page` until that key stops appearing.

   <Callout type="warn" title="Rewrite next_page to https before following it">
     Every `next_page` and `previous_page` URL is generated with the `http` scheme and `301`s to `https`. HTTP clients that don't forward `Authorization` across a scheme-changing redirect will drop it and get a `401`. Rewrite the scheme before requesting the URL, or use `curl -L --location-trusted`.
   </Callout>

   Note also that these keys are omitted when they don't apply rather than set to `null`, so test for presence, not for `!== null`. See [Pagination](/docs/reference/v3/pagination).

7. **Change how your code reads write responses.**

   V3 returns the full entity on a create, so code that reads a create response keeps working. An update returns nothing at all, so code that reads a PATCH response has to change.

   | Operation | V3 response |
   |---|---|
   | Create | `201` with the full created entity |
   | Update (PATCH) | `204` with no body |
   | Delete | `204` with no body |
   | Duplicate on create | `409` |

   Anywhere your V1 code reads values out of a PATCH response, add a follow-up GET instead.

   <Callout type="warn" title="PATCH recently changed to 204">
     Earlier V3 releases returned `200` with the full updated entity on PATCH. It now returns `204` with an empty body, so an integration written against the older behavior breaks on any code that parses an update response. POST is unaffected: it still returns `201` with the full created entity.
   </Callout>

8. **Re-check your delete and update logic before you run it.**

   Two V3 behaviors catch migrated code out:

   - **PATCH replaces the `attributes` map rather than merging into it.** Sending only the attributes that changed deletes every attribute you left out, with no error and no warning. Read the current map, merge, then send it back, or use `PATCH /products/{identifier}/attributes/{name}` with a bare value to scope the change to one attribute.
   - **DELETE erases** the entity or the field it's applied to. It doesn't set the value to null or reset it to a default, and removing a field can cause inheritance to resolve for it instead. Confirm on a test record that a delete does what your V1 code assumed.

   See [Update and delete records](/docs/reference/v3/updates-and-deletes).

9. **Run both versions side by side before cutting over.**

   Point a copy of your integration at V3 while the V1 one keeps running, and compare the results: record counts from the same filter, the fields that come back, and the relations each product reports. A count that differs usually means a filter didn't translate the way you expected, and it's far cheaper to find that in a comparison than in production. Since V3 won't give you a total, get the count by paging to the end on both sides.

## Troubleshooting

Check the problems below if you run into issues while following this guide.

<Accordions type="multiple">
  <Accordion title="A v3 search returns everything, ignoring your filter" value="search-returns-everything">
    A search with no recognized filter means "get all," and an unrecognized parameter is common when you type the bracket syntax by hand. Check the bracket syntax and the URL encoding, then compare counts against the same V1 filter before you trust a converted query.
  </Accordion>

  <Accordion title="Your code breaks after a successful update" value="code-breaks-after-update">
    V3's PATCH returns `204` with an empty body. Code that checks for `200`, or that parses the response, fails even though the write succeeded. Read the updated values with a follow-up GET, and audit every place your V1 code branches on a write's status code or reads its body before you switch versions.
  </Accordion>

  <Accordion title="Attributes you didn't touch disappeared after an update" value="attributes-disappeared">
    PATCH replaced the whole `attributes` map with what you sent. Restore the missing values, then switch to read-merge-write, or patch one attribute at a time through `PATCH /products/{identifier}/attributes/{name}`.
  </Accordion>

  <Accordion title={<>A link request returns <code>404</code> or <code>405</code></>} value="link-request-404-405">
    Use the dedicated link and unlink endpoints from step 5. `category_ids` and `static_list_ids` are no longer accepted on create or update, and the generic `DELETE /products/{identifier}/{path}` form isn't a scoped unlink.
  </Accordion>

  <Accordion title="Results are missing fields you used to get" value="results-missing-fields">
    Field selection moved from the `attributes` body key to query parameters. Add the fields with `_fields`, repeated once per field.
  </Accordion>

  <Accordion title={<>Following a <code>next_page</code> URL returns <code>401</code></>} value="next-page-401">
    The URL came back as `http` and redirected to `https`, and your client dropped the `Authorization` header. Rewrite the scheme to `https` before requesting it.
  </Accordion>

  <Accordion title="You can't find the v3 endpoint for uploading asset content or attaching an asset to a product" value="no-v3-asset-endpoint">
    There isn't one. Both operations stay on V1, as step 1 explains.
  </Accordion>
</Accordions>
