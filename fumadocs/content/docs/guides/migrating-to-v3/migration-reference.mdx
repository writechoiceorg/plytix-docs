This page maps v1 and v2 to v3: base URLs, authentication, request and response shapes, filter operators, and every endpoint with its v3 equivalent or its absence. For the process of moving an integration across, and for deciding which calls move at all, see [Migrating to v3](/docs/guides/migrating-to-v3).

Where an operation has no v3 equivalent, the table says so rather than guessing at the nearest match.

## Base URLs and authentication

| | v1 and v2 | v3 |
|---|---|---|
| Base URL | `https://pim.plytix.com` | `https://pim.plytix.com` |
| Path prefix | `/api/v1`, `/api/v2` | `/api/v3` |
| Auth service | `https://auth.plytix.com` | Same |
| Token request | `POST /auth/api/get-token` with `api_key` and `api_password` | Same |
| Request header | `Authorization: Bearer <token>` | Same |

Credentials, their roles, and token-refresh logic carry over unchanged, and the same token works against both versions. That matters, because an integration that keeps some calls on v1 doesn't need a second auth flow. See [Quickstart](/docs/guides/quickstart).

## Request shape

The structural change: a v1 search is a POST with a JSON body, and a v3 search is a GET with query parameters.

| | v1 and v2 | v3 |
|---|---|---|
| Search verb and path | `POST /api/v1/<entities>/search` | `GET /api/v3/<entities>` |
| Filters | `filters` array in the body | Query parameters in bracket syntax |
| Field selection | `attributes` array in the body | `_fields=<name>`, repeated per field |
| Paging | `pagination` object in the body | `_page`, `_page_size`, `_sort_by` |
| No filter given | Body required | Returns all records |

## Filter operators

v1 expresses a filter as an object with `field`, `operator`, and `value`. v3 puts the operator in brackets after the field name. Equality needs no operator at all.

| Meaning | v1 operator | v3 syntax |
|---|---|---|
| Equals | `eq` | `field=value` or `field[eq]=value` |
| Not equal | `!eq` | `field[!eq]=value` |
| In a set | `in` | `field[in]=value1&field[in]=value2` |
| Not in a set | `!in` | `field[!in]=value1&field[!in]=value2` |
| Greater than | `gt` | `field[gt]=value` |
| Greater or equal | `gte` | `field[gte]=value` |
| Less than | `lt` | `field[lt]=value` |
| Less or equal | `lte` | `field[lte]=value` |
| Between | Two comparisons | `field[gte]=<low>&field[lte]=<high>` |
| Contains, case-insensitive | `contains` | `field[icontains]=value` |
| Contains, case-sensitive | `contains` | `field[contains]=value` |
| Field exists | `exists` | `field[exists]=true` |
| Field does not exist | `!exists` | `field[!exists]=true` |
| Field is null | `null` | `field[null]` |
| Field is not null | `!null` | `field[!null]` |
| Empty string or empty list | Not available | `field[length][eq]=0` |
| Arrays intersect | Not available | `field[intersects]=value`, negated as `field[!intersects]=value` |
| Length comparison | Not available | `field[length][gt]=value`, and the other comparison operators |
| Days since a date | Not available | `field[days_passed][gt]=7`, optionally `field[days_passed:Europe/Madrid][lt]=1` |

[Filtering and Query Syntax](/docs/reference/v3/filtering-query-syntax) covers each operator in full, along with the gotchas. Note that the case-insensitive contains operator is `icontains`; some older Plytix material calls it `contains:ignorecase`, which the API does not accept.

### Boolean grouping

| Logic | v1 | v3 |
|---|---|---|
| A AND B | Both objects in the same inner array `[[A, B]]` {/* [PENDING] */} | `A&B` |
| A OR B | Separate inner arrays `[[A], [B]]` {/* [PENDING] */} | `_or[0]A&_or[0]B` |
| (A OR B) AND (C OR D) | Not expressible directly | `_or[0]A&_or[0]B&_or[1]C&_or[1]D` |
| (A AND B) OR (C AND D) | Not expressible directly | `_or[0]_and[0]A&_or[0]_and[0]B&_or[0]_and[1]C&_or[0]_and[1]D` |
| NOT (A OR B) | Not available | `_!or[0]A&_!or[0]B` |

### Custom attributes and related entities

| Target | v1 | v3 |
|---|---|---|
| Custom attribute | `{"field": "attributes.name", "operator": "<op>", "value": "<value>"}` | `attributes.name[<op>]=value` |
| Related entity field | Not possible | `related-entity.attribute[<op>]=value` |
| Product relationships | `relationship_filters` with nested `product_ids` objects | `product_relationships.relationship_id=<id>&product_relationships.related_product_id=<id>` |

<Callout type="info" title="One restriction to know about">
  The `_!exists` form on relationships is restricted: it's allowed only for `relationships.id` or `relationships.label`, and only when not grouped with `_and` or `_or`.
</Callout>

## Pagination

| | v1 and v2 | v3 |
|---|---|---|
| Request | `"pagination": {"page": 1, "page_size": 25, "order": "sku"}` in the body | `_page=1&_page_size=25&_sort_by=sku` in the query string |
| Bounds | Not documented | `_page >= 1` and `_page_size <= 1000` — both return `422` outside those bounds |
| Record counts | `total_count` always returned | None available |
| Response keys | `count`, `order`, `page`, `page_size`, `total_count` | `next_page`, `previous_page` |

v3 returns page URLs rather than a page number to increment, so a paging loop follows `next_page` until that key stops appearing instead of counting pages. The keys are omitted when they don't apply rather than set to `null`, so a client written as `if (pagination.next_page !== null)` is wrong — test for presence.

<Callout type="warn" title="No counts in v3">
  v1 returned `total_count` on every search. v3 has no equivalent: the pagination block carries no counts, and there is no parameter that adds one. Requesting `_total_count` or `_filtered_count` returns `400 InvalidFieldError`.

  This is a capability regression from v1, not just an undocumented feature. Anything in your integration that reads a total — a progress bar, a "showing N of M" label, a pre-sized buffer — has to page to the end and tally. See [Pagination](/docs/reference/v3/pagination).
</Callout>

<Callout type="warn" title="next_page URLs use the http scheme">
  Every `next_page` and `previous_page` link comes back as `http://`, then `301`s to `https`. Clients that don't forward `Authorization` across a scheme-changing redirect drop it and get a `401`. Rewrite the scheme before following the link, or use `curl -L --location-trusted`.
</Callout>

## Response conventions

| Operation | v1 and v2 | v3 |
|---|---|---|
| Search | `200` with `data` and `pagination` | `200` with `data` and `pagination` |
| Get one | `200` with the record | `200` with the record, `data` as an object and no `pagination` key |
| Create | `200` or `201` with the created entity | `201` with the full created entity |
| Duplicate on create | Varies | `409` |
| Update (PATCH) | Returns the modified entity | `204` with no body |
| Delete | Varies | `204` with no body |
| Accepted for async processing | Not applicable | `202` with a `process_id` |
| Error | Varies | `errors` array in the same envelope, each entry `{"name": "...", "description": "..."}`. See [Errors and Status Codes](/docs/reference/v3/errors-status-codes) |

Three behavioral differences matter more than the status codes:

- **v3 returns nothing on an update.** v1's PATCH returned the modified entity; v3's returns `204` with an empty body, so any code that read values out of an update response needs a follow-up GET. Create is unchanged in this respect: it still returns the full entity.
- **v3 PATCH replaces a map field you name.** Sending part of a product's `attributes` deletes the attributes you left out. Read the current map, merge, then send it back, or patch a single attribute through `PATCH /products/{identifier}/attributes/{name}` with a bare value. See [Working with Updates and Deletes](/docs/reference/v3/updates-and-deletes).
- **v3 DELETE erases** the entity or field rather than setting it to null or a default, and removing a field can cause inheritance to resolve for it.

<Callout type="warn" title="PATCH recently changed to 204">
  Earlier v3 releases returned `200` with the full updated entity on PATCH. It now returns `204` with an empty body, so an integration written against the older behavior breaks on any code that parses an update response. POST is unaffected: it still returns `201` with the full created entity.
</Callout>

## Linking and unlinking

v1 links through dedicated subpaths. v3 originally accepted `category_ids` and `static_list_ids` arrays on create and update; those fields are no longer accepted, leaving the dedicated link and unlink endpoints as the only route.

| Link | v1 | v3 |
|---|---|---|
| Product to category | `POST /api/v1/products/{product_id}/categories` | `POST /api/v3/products/{identifier}/categories` |
| Product from category | `DELETE /api/v1/products/{product_id}/categories/{category_id}` | `DELETE /api/v3/products/{identifier}/categories/{id}` |
| Asset to category | Through `category_ids` on the asset | `POST /api/v3/assets/{identifier}/categories` |
| Asset from category | Through `category_ids` on the asset | `DELETE /api/v3/assets/{identifier}/categories/{id}` |
| Attribute to group | `POST /api/v1/attribute-groups/product` | `POST /api/v3/product-attributes/{identifier}/groups` |
| Attribute from group | Not available | `DELETE /api/v3/product-attributes/{identifier}/groups/{id}` |
| Product to asset | `POST /api/v1/products/{product_id}/assets` | **No v3 equivalent.** Stays on v1 |
| Product from asset | `DELETE /api/v1/products/{product_id}/assets/{asset_id}` | **No v3 equivalent.** Stays on v1 |
| Product to family | `POST /api/v1/products/{product_id}/family` | `PATCH /api/v3/products/{identifier}` with `product_family_id` |

<Callout type="warn" title="The generic subpath DELETE is not an unlink">
  `DELETE /api/v3/products/{identifier}/{path}` doesn't remove a single linked record. A collection path such as `categories` returns `405`, and an unrecognized path returns `404`. Use the specific unlink endpoints above.
</Callout>

## Endpoint mapping

### Products

| v1 or v2 | v3 |
|---|---|
| `POST /api/v1/products` | `POST /api/v3/products` |
| `POST /api/v1/products/search` | `GET /api/v3/products` |
| `GET /api/v1/products/{product_id}` | `GET /api/v3/products/{identifier}` |
| `PATCH /api/v1/products/{product_id}` | `PATCH /api/v3/products/{identifier}` |
| `DELETE /api/v1/products/{product_id}` | `DELETE /api/v3/products/{identifier}` |
| `GET /api/v1/products/{product_id}/assets` | `GET /api/v3/products?_fields=assets` |
| `POST /api/v1/products/{product_id}/assets` | No equivalent. Stays on v1 |
| `DELETE /api/v1/products/{product_id}/assets/{asset_id}` | No equivalent. Stays on v1 |
| `GET /api/v1/products/{product_id}/categories` | `GET /api/v3/products?_fields=categories` |
| `POST /api/v1/products/{product_id}/categories` | `POST /api/v3/products/{identifier}/categories` |
| `DELETE /api/v1/products/{product_id}/categories/{category_id}` | `DELETE /api/v3/products/{identifier}/categories/{id}` |
| `POST /api/v1/products/{product_id}/family` | `PATCH /api/v3/products/{identifier}` with `product_family_id` |

In v3, `{identifier}` accepts either the product ID or the SKU, URL-encoded.

The two read rows above map to the search endpoint rather than to v3's own `/products/{identifier}/categories` and `/products/{identifier}/assets` subpaths. Those subpaths exist, but they currently return an empty array even for a product that genuinely has those relations; `_fields` expansion on a search returns the data correctly. The `relationships` and `attributes` subpaths are unaffected and can be used directly.

### Variants

v3 has no variant endpoints. A variant is an ordinary product that names its parent, so creation and deletion go through the regular product endpoints.

| v1 or v2 | v3 |
|---|---|
| `POST /api/v1/products/{parent_product_id}/variants` | `POST /api/v3/products` with `parent_id` and `product_family_id` |
| `GET /api/v1/products/{product_id}/variants` | `GET /api/v3/products?parent_id=<parent_id>` {/* [PENDING] */} |
| `DELETE /api/v1/products/{parent_product_id}/variant/{variant_id}` | `DELETE /api/v3/products/{identifier}` |
| `POST /api/v1/products/{parent_product_id}/variants/resync` | No equivalent. Stays on v1 |

A product's position in the hierarchy is reported by `product_level`: `0` SINGLE, `1` PARENT, `2` VARIANT, `3` SUB_VARIANT. A standalone product starts at `0` and becomes `1` as soon as another product references it through `parent_id`. See [Reconstruct parent/variant hierarchies](/docs/guides/reconstructing-parent-variant-hierarchies).

{/* FLAG (open):
  Listing a parent's variants with `?parent_id=<id>` is marked [PENDING] — it follows from `parent_id` being a real product field, but filtering on it was never tested, and [Reconstruct parent/variant hierarchies](/docs/guides/reconstructing-parent-variant-hierarchies) reads the hierarchy from the parent's own `num_variations` instead. Verify with `endpoint-tester` before publishing, or drop the row and point at the parent-read method.

## Endpoints with no v3 equivalent

These v1 paths have no counterpart in the v3 spec. The first four keep working on v1 and are the usual reason an integration stays split across versions.

| v1 endpoint | What to do |
|---|---|
| `PUT /api/v1/assets/{asset_id}/content` | Keep on v1. v3 takes content only at asset creation |
| `POST` and `DELETE /api/v1/products/{product_id}/assets[/{asset_id}]` | Keep on v1. v3 has no product-to-asset link path. `thumbnail_id` on the product sets a single image, which is not the same thing |
| `GET /api/v1/filters/product`, `/filters/asset`, `/filters/relationships` | Keep on v1, or build filters from the attribute definitions returned by `GET /api/v3/product-attributes` |
| `POST /api/v1/products/{parent_product_id}/variants/resync` | Keep on v1 |
| `POST /api/v1/accounts/api-credentials/search` | Manage API keys in the Plytix interface, under the **API** tab |
| `POST /api/v1/accounts/memberships/search` | Manage users in the Plytix interface, under the **Team** tab |

### Bulk operations

Neither v1 nor v3 offers bulk writes as a generally available feature. The v3 bulk API is restricted to large and enterprise accounts; contact your account manager to find out whether your account has access. See [Bulk operations for large catalogs](/docs/guides/bulk-operations-for-large-catalogs).

## What v2 covers

v2 is a products-only beta served from the same base URL. It mirrors the v1 product endpoints and adds two operations v1 lacks: `DELETE /api/v2/products/{product_id}/relationships/{relationship_id}` and `DELETE /api/v2/products/{product_id}/categories/{category_id}`. Everything outside products, including assets, attributes, categories, families, and relationship definitions, stays on v1.
