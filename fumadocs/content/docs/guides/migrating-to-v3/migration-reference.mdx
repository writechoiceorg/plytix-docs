This page maps v1 and v2 to v3: base URLs, authentication, request and response shapes, filter operators, and every endpoint with its v3 equivalent. For the process of moving an integration across, see [Migrating to v3](/docs/guides/migrating-to-v3).

<Callout type="warn" title="FLAG">
  Sources and their limits, all of which affect this page:

  - `openapi_pimv1.json` was converted from the Plytix PIM v1 Postman collection, and its own description says the shapes were inferred from saved examples and haven't been verified against the live API.
  - `openapi_pimv3.json` is a FastAPI export with no `servers`, no `securitySchemes`, and no documented query parameters, so the base URL, auth, and search parameters below come from `API V3.md` and the existing guides instead.
  - `API V3.md` is a design document with approved, rejected, and postponed options. Parts of it describe intended rather than shipped behavior.

  Verify every row with the `endpoint-tester` skill before publishing. Rows marked `[PENDING]` are ones where no source gives a confident mapping.
</Callout>

## Base URLs and authentication

| | v1 and v2 | v3 |
|---|---|---|
| Base URL | `https://pim.plytix.com` | `https://<v3-base-url>` `[PENDING]` |
| Path prefix | `/api/v1`, `/api/v2` | `/api/v3` |
| Auth service | `https://auth.plytix.com` | Same `[PENDING]` |
| Token request | `POST /auth/api/get-token` with `api_key` and `api_password` | Same `[PENDING]` |
| Request header | `Authorization: Bearer <token>` | Same |

Credentials, their roles, and token-refresh logic carry over unchanged. See [Quickstart](/docs/guides/quickstart).

## Request shape

The structural change: a v1 search is a POST with a JSON body, and a v3 search is a GET with query parameters.

| | v1 and v2 | v3 |
|---|---|---|
| Search verb and path | `POST /api/v1/<entities>/search` | `GET /api/v3/<entities>` |
| Filters | `filters` array in the body | Query parameters in bracket syntax |
| Field selection | `attributes` array in the body | `_fields=<name>`, repeated per field |
| Paging | `pagination` object in the body | `_page`, `_page_size`, `_sort_by` |
| No filter given | Body required | Returns all records |

## Filter operators

v1 expresses a filter as an object with `field`, `operator`, and `value`. v3 puts the operator in brackets after the field name. Equality needs no operator at all.

| Meaning | v1 operator | v3 syntax |
|---|---|---|
| Equals | `eq` | `field=value` or `field[eq]=value` |
| Not equal | `!eq` | `field[!eq]=value` |
| In a set | `in` | `field[in]=value1&field[in]=value2` |
| Not in a set | `!in` | `field[!in]=value1&field[!in]=value2` |
| Greater than | `gt` | `field[gt]=value` |
| Greater or equal | `gte` | `field[gte]=value` |
| Less than | `lt` | `field[lt]=value` |
| Less or equal | `lte` | `field[lte]=value` |
| Between | Two comparisons | `field[gte]=<low>&field[lte]=<high>` |
| Contains, case-insensitive | `contains` | `field[contains:ignorecase]=value` |
| Contains, case-sensitive | `contains` | `field[contains]=value` |
| Field exists | `exists` | `field[exists]` |
| Field does not exist | `!exists` | `field[!exists]` |
| Field is null | `null` | `field[null]` |
| Field is not null | `!null` | `field[!null]` |
| Empty string or empty list | Not available | `field[len]=0` |
| Arrays intersect | Not available | `field[intersects]=value`, negated as `field[!intersects]=value` |
| Length comparison | Not available | `field[length][gt]=value`, and the other comparison operators |
| Days since a date | Not available | `field[days_passed][gt]=7`, optionally `field[days_passed:Europe/Madrid][lt]=1` |

### Boolean grouping

| Logic | v1 | v3 |
|---|---|---|
| A AND B | Both objects in the same inner array `[[A, B]]` `[PENDING]` | `A&B` |
| A OR B | Separate inner arrays `[[A], [B]]` `[PENDING]` | `_or[0]A&_or[0]B` |
| (A OR B) AND (C OR D) | Not expressible directly | `_or[0]A&_or[0]B&_or[1]C&_or[1]D` |
| NOT (A OR B) | Not available | `_!or[0]A&_!or[0]B` |

The v1 rows are marked `[PENDING]` because the nesting semantics come from the Postman-derived spec's saved example rather than from documented behavior.

### Custom attributes and related entities

| Target | v1 | v3 |
|---|---|---|
| Custom attribute | `{"field": "attributes.name", "operator": "<op>", "value": "<value>"}` | `attributes.name[<op>]=value` |
| Related entity field | Not possible | `related-entity.attribute[<op>]=value` |
| Product relationships | `relationship_filters` with nested `product_ids` objects | `product_relationships.relationship_id=<id>&product_relationships.related_product_id=<id>` |

<Callout type="info" title="One restriction to know about">
  `API V3.md` restricts the `_!exists` form on relationships for the public v3 API: it's allowed only for `relationships.id` or `relationships.label`, and only when not grouped with `_and` or `_or`.
</Callout>

## Pagination

| | v1 and v2 | v3 |
|---|---|---|
| Request | `"pagination": {"page": 1, "page_size": 25, "order": "sku"}` in the body | `_page=1&_page_size=25&_sort_by=sku` |
| Optional counts | Always returned | `_filtered_count=<bool>`, `_total_count=<bool>` |
| Response keys | `count`, `order`, `page`, `page_size`, `total_count` | `next_page`, `previous_page` |

v3 returns page URLs rather than a page number to increment, so a paging loop follows `next_page` until it's null instead of counting pages. The v3 `Pagination` schema carries no counts, so a migrated loop can't rely on a total. See [Pagination](/docs/reference/v3/pagination).

## Response conventions

| Operation | v1 and v2 | v3 |
|---|---|---|
| Search | `200` with `data` and `pagination` | `200` with `data` and `pagination` |
| Get one | `200` with the record | `200` with the record |
| Create | `200` or `201` with the created entity | `201` with the full created entity |
| Update (PATCH) | Returns the modified entity | `200` with the full updated entity |
| Delete | Varies | `204` with no body |
| Accepted for async processing | Not applicable | `202` with a `process_id` |
| Error | Varies | `errors` array in the same envelope, each entry `{"name": "...", "description": "..."}`. See [Errors and Status Codes](/docs/reference/v3/errors-status-codes) |

Two behavioral differences matter more than the status codes:

- **v3 returns the full entity on a write**, not just the fields you sent, so a PATCH response is the whole record. This matches v1's behavior, so response-parsing code generally carries over; code that branches on an exact status code does not.
- **v3 DELETE erases** the entity or field rather than setting it to null or a default, and removing a field can cause inheritance to resolve for it.

<Callout type="warn" title="Plytix's internal reference states the opposite">
  `API V3.md` describes v3 write endpoints as returning only an ID, with PATCH returning `204`. Live testing contradicts this on every resource tested. The table above is what the API actually does.
</Callout>

## Endpoint mapping

### Products

| v1 or v2 | v3 |
|---|---|
| `POST /api/v1/products` | `POST /api/v3/products` |
| `POST /api/v1/products/search` | `GET /api/v3/products` |
| `GET /api/v1/products/{product_id}` | `GET /api/v3/products/{identifier}` |
| `PATCH /api/v1/products/{product_id}` | `PATCH /api/v3/products/{identifier}` |
| `DELETE /api/v1/products/{product_id}` | `DELETE /api/v3/products/{identifier}` |
| `GET /api/v1/products/{product_id}/assets` | `GET /api/v3/products/{identifier}/assets`, or field expansion on the product |
| `POST /api/v1/products/{product_id}/assets` | `POST /api/v3/products/{identifier}/assets` |
| `DELETE /api/v1/products/{product_id}/assets/{asset_id}` | `DELETE /api/v3/products/{identifier}/assets/{asset_id}` |
| `GET /api/v1/products/{product_id}/categories` | `GET /api/v3/products/{identifier}/categories`, or field expansion |
| `POST /api/v1/products/{product_id}/categories` | `POST /api/v3/products/{identifier}/categories` |
| `DELETE /api/v1/products/{product_id}/categories/{category_id}` | `DELETE /api/v3/products/{identifier}/categories/{category_id}` |
| `POST /api/v1/products/{product_id}/family` | `PATCH /api/v3/products/{identifier}` `[PENDING]` |

In v3, `{identifier}` accepts either the product ID or the SKU, URL-encoded. The subresource paths above use v3's generic `/{identifier}/{path}` pattern, which the spec defines but doesn't enumerate per field.

## Endpoints with no v3 equivalent

These v1 paths have no counterpart in `openapi_pimv3.json`. Check whether your integration depends on any of them before planning a cutover.

| v1 endpoint | What to do instead |
|---|---|
| `GET /api/v1/filters/product`, `/filters/asset`, `/filters/relationships` | No filter-discovery endpoint in v3. Build filters from the attribute definitions returned by `GET /api/v3/product-attributes` |
| `PUT /api/v1/assets/{asset_id}/content` | No asset content upload in the v3 spec `[PENDING]` |
| `POST /api/v1/products/{parent_product_id}/variants` | No variant endpoints in v3. Variants are modeled through product families and product family models `[PENDING]` |
| `POST /api/v1/products/{parent_product_id}/variants/resync` | No equivalent `[PENDING]` |
| `DELETE /api/v1/products/{parent_product_id}/variant/{variant_id}` | No equivalent `[PENDING]` |
| `GET /api/v1/products/{product_id}/variants` | No equivalent `[PENDING]` |
| `POST /api/v1/accounts/api-credentials/search` | Manage API keys in the Plytix interface, under the **API** tab |
| `POST /api/v1/accounts/memberships/search` | Manage users in the Plytix interface, under the **Team** tab |

<Callout type="warn" title="FLAG">
  **Bulk operations.** `API V3.md` specifies a full bulk API at `api/v3/-/bulk/<entities>` with job tracking at `api/v3/-/bulk/-/jobs/`, but no bulk path exists in `openapi_pimv3.json`, and [Bulk operations for large catalogs](/docs/guides/bulk-operations-for-large-catalogs) states there are none today. Neither v1 nor v3 offers bulk writes in their specs. Confirm the timeline with Plytix before documenting the bulk paths here.
</Callout>

The Channels row is marked `[CONFLICT]` because the project's source materials state that Channels are configured only in the Plytix interface, while the spec defines full CRUD for them. See the Notes in `information-architecture.md`.

## What v2 covers

v2 is a products-only beta served from the same base URL. It mirrors the v1 product endpoints and adds two operations v1 lacks: `DELETE /api/v2/products/{product_id}/relationships/{relationship_id}` and `DELETE /api/v2/products/{product_id}/categories/{category_id}`. Everything outside products, including assets, attributes, categories, families, and relationship definitions, stays on v1.
