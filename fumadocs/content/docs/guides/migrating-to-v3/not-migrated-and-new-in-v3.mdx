Not every V1 call has a V3 counterpart yet. This page lists the V1 endpoints missing from the current V3 contract, the entry points that are new in V3, and the slice of the API that V2 covers. It reflects the V3 OpenAPI dated 2026-10-19 and will change as V3 expands. Keep a legacy call wherever your integration needs a capability with no confirmed public V3 equivalent, and move everything else to V3. It's part of the reference set for [Migration overview](/guides/migrating-to-v3).

Each entry below falls into one of these groups:

- **Legacy only:** documented in V1 and absent from the current V3 contract. Keep calling V1.
- **Alternative in V3:** V3 has no matching endpoint but does the job another way. Where that way isn't confirmed yet, the entry says so.
- **Planned:** described in Plytix's V3 design, but not part of the current V3 contract.

## V1 endpoints missing from the V3 contract

The endpoints below remain documented in the [V1/V2 reference](/reference/v1-v2/api-v1-v2-reference), and none of them has a matching endpoint in the current V3 contract. [Endpoint mapping](/guides/migrating-to-v3/endpoint-mapping) gives the V3 outcome for every V1/V2 endpoint, including the ones with an equivalent.

| V1 endpoint | Status | What to do |
|---|---|---|
| `PUT /api/v1/assets/{asset_id}/content` | Legacy only | Keep on V1. V3 takes a file only when it creates an asset. An asset update changes `filename` and `alt_text`, not the file. |
| `POST` and `DELETE /api/v1/products/{product_id}/assets[/{asset_id}]` | Alternative in V3 | V3 has no product-to-asset link path. You set a media or media gallery attribute to the asset ID with `PATCH /api/v3/products/{identifier}/attributes/{label}`, and `thumbnail_id` sets the main image. A media attribute takes a bare asset ID and a media gallery attribute takes an array of IDs; objects such as `{"id": "<asset_id>"}` are rejected. To remove one asset, `DELETE` on a media attribute's path clears its single asset, but on a gallery it clears every asset: write the gallery's remaining IDs instead, as in [Remove one asset from a gallery](/guides/safely-removing-categories-assets-or-relationships#remove-one-asset-from-a-gallery). Removing an asset from a product doesn't delete the asset. |
| `GET /api/v1/filters/product`, `/filters/asset`, `/filters/relationships` | Legacy only | Keep on V1 to discover the available fields and operators. `GET /api/v3/product-attributes` returns your product attribute definitions, including each attribute's `type`, but not system fields, asset or relationship fields, or the supported operators. See [Filtering and search](/reference/v3/filtering-and-search) for the operators V3 supports. |
| `POST /api/v1/products/{parent_product_id}/variants/resync` | Legacy only | Keep on V1. |
| `POST /api/v1/accounts/api-credentials/search` | Legacy only | Keep on V1. You can manage API keys in the Plytix dashboard under the **API** tab, but that doesn't replace searching them through the API. |
| `POST /api/v1/accounts/memberships/search` | Legacy only | Keep on V1. You can manage users in the Plytix dashboard, but that doesn't replace searching them through the API. |
| `POST /api/v1/product_families/{product_family_id}/all_attributes/edit` | Alternative in V3, partial | Change each custom attribute's `level` with `PATCH /api/v3/product-families/{product_family_id}/attributes/{attribute_id}`. V3 has no documented way to set inheritance for system attributes, so keep that on V1. |
| Relationship types (`/api/v1/relationships`), and adding, updating, or removing related products (`/api/v1/products/{product_id}/relationships/{relationship_id}` and its `/unlink`, plus their V2 counterparts) | Planned | Keep on V1/V2. V3's earlier relationship routes are retired, and their replacement, product relationship types, isn't documented yet. See [Product relationships](/guides/migrating-to-v3/endpoint-mapping#product-relationships). |

## Bulk operations

The current V3 contract has no bulk create, update, or delete endpoints. Bulk endpoints are part of Plytix's V3 design (planned), but there's no V3 bulk call to migrate to yet. To change many products in V3, send single-item requests paced under your [rate limit](/reference/v3/rate-limits).

## New entry points in V3

These V3 entry points have no V1 path of their own. One is a new resource. The other is a new top-level view of associations that V1 already managed under families. The list isn't exhaustive; see the [V3 API reference](/reference/v3) for every resource.

| V3 entry point | What it is | Managed through |
|---|---|---|
| `/api/v3/asset-lists` | A new resource: saved asset lists | Its own endpoints |
| `/api/v3/family-attributes` | A view of family-to-attribute associations and their levels. Narrow it with `product_family_id` | Read-only here. Link, change, and unlink attributes through `/api/v3/product-families/{product_family_id}/attributes` |

## What V2 covers

V2 is a products-only beta served from the same base URL. It covers a subset of the V1 product endpoints. Its `DELETE /api/v2/products/{product_id}/relationships/{relationship_id}` removes products from a relationship, the same job V1 does with `/api/v1/products/{product_id}/relationships/{relationship_id}/unlink`, so it's a different route rather than a new capability. Everything outside products, including assets, attributes, categories, families, and relationship definitions, stays on V1.
