A v1 search is a POST with a JSON body. A v3 search is a GET with query parameters. This page maps the two request shapes onto each other and covers what changes once the results come back, including the two pagination behaviors that break migrated paging loops. It's part of the reference set for [Migrating to v3](/docs/guides/migrating-to-v3).

## Request shape

The structural change is the verb: what used to be a POST body is now a query string on a GET.

| | v1 and v2 | v3 |
|---|---|---|
| Search verb and path | `POST /api/v1/<entities>/search` | `GET /api/v3/<entities>` |
| Filters | `filters` array in the body | Query parameters in bracket syntax |
| Field selection | `attributes` array in the body | `_fields=<name>`, repeated per field |
| Paging | `pagination` object in the body | `_page`, `_page_size`, `_sort_by` |
| No filter given | Body required | Returns all records |

That last row is worth pausing on. A v3 search with no recognized parameter means "get all," so a filter that fails to translate doesn't error, it quietly returns the whole collection. [Filter operators](/docs/guides/migrating-to-v3/filter-operators) covers the syntax each v1 operator becomes.

## Pagination

Both versions page, but v3 reports its position differently and drops counts entirely.

| | v1 and v2 | v3 |
|---|---|---|
| Request | `"pagination": {"page": 1, "page_size": 25, "order": "sku"}` in the body | `_page=1&_page_size=25&_sort_by=sku` in the query string |
| Bounds | Not documented | `_page >= 1` and `_page_size <= 1000`; both return `422` outside those bounds |
| Record counts | `total_count` always returned | None available |
| Response keys | `count`, `order`, `page`, `page_size`, `total_count` | `next_page`, `previous_page` |

v3 returns page URLs rather than a page number to increment, so a paging loop follows `next_page` until that key stops appearing instead of counting pages. The keys are omitted when they don't apply rather than set to `null`, so a client written as `if (pagination.next_page !== null)` is wrong, test for presence.

<Callout type="warn" title="No counts in v3">
  v1 returned `total_count` on every search. v3 has no equivalent: the pagination block carries no counts, and there is no parameter that adds one. Requesting `_total_count` or `_filtered_count` returns `400 InvalidFieldError`.

  This is a capability regression from v1, not just an undocumented feature. Anything in your integration that reads a total (a progress bar, a "showing N of M" label, a pre-sized buffer) has to page to the end and tally. See [Pagination](/docs/reference/v3/pagination).
</Callout>

<Callout type="warn" title="next_page URLs use the http scheme">
  Every `next_page` and `previous_page` link comes back as `http://`, then `301`s to `https`. Clients that don't forward `Authorization` across a scheme-changing redirect drop it and get a `401`. Rewrite the scheme before following the link, or use `curl -L --location-trusted`.
</Callout>
