This tutorial takes you from an empty terminal to a real response from your own catalog. You'll create an API key in the Plytix dashboard, trade it for a bearer token, and use that token to read products out of your account. It's written for anyone starting an integration, whether you're syncing an ERP, building an export, or sizing up what the API returns before you plan anything.

**Learning objectives:** By the end of this tutorial, you will be able to:

- Create and manage API credentials in the Plytix dashboard
- Exchange those credentials for a bearer token, and know when it expires
- Make an authenticated request and read the response envelope Plytix returns

## Before you begin

Make sure you have the following:

- **A Plytix account with Owner or Admin rights.** Only Owners and Admins can create API keys. If you don't have those rights, ask an account Owner or Admin to complete step 1 and send you the credentials.
- **A terminal with `curl`,** or any HTTP client you prefer. Every example here is a `curl` command you can paste and run.

You don't need to request API access or wait for approval. Key creation is self-service.

## Step 1: Create your API credentials

An API key is a key and password pair that identifies your integration to Plytix. You create it once in the dashboard.

1. Sign in at [accounts.plytix.com](https://accounts.plytix.com).
2. Open the **API** tab.
3. Create a key, giving it a name and a role. The role decides what the key can reach, so pick the narrowest one that covers what you're building.
4. Copy the **API key** and the **API password** using the clipboard icon beside each.

Store both somewhere safe before you leave the page. You can rename, re-role, or delete a key later from the same tab, but changing an existing key's role can break whatever is already using it, so prefer creating a new key per integration.

## Step 2: Exchange your credentials for a token

Plytix uses bearer tokens. Rather than sending your key and password on every request, you trade them once for a token and send that instead.

Note the host: tokens come from `auth.plytix.com`, which is a different service from the PIM API you'll call in step 3.

<Tabs items={['Request', 'Response']}>
  <Tab value="Request">
    ```bash
    curl --request POST \
      --url https://auth.plytix.com/auth/api/get-token \
      --header 'Content-Type: application/json' \
      --data '{
        "api_key": "your.api.key",
        "api_password": "your.secret.api.password"
      }'
    ```
  </Tab>
  <Tab value="Response">
    ```json
    {
      "data": [
        {
          "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
          "refresh_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9..."
        }
      ]
    }
    ```
  </Tab>
</Tabs>

Take `access_token` from `data[0]`. Every request after this needs it in an `Authorization: Bearer <token>` header.

<Callout type="warn" title="Tokens expire after 15 minutes">
  Request a new token when you get a `401`, and build that refresh into any job that runs longer than a few minutes. A response also carries a `refresh_token`, treat it as unsupported and request a fresh token the same way you got the first one.
</Callout>

If the credentials are wrong, you'll get a `401` with the message nested under an `error` key:

```json
{
  "error": {
    "msg": "Bad api_key or api_password: Query did not throw any results",
    "errors": [{ "field": "http_status_code", "msg": 401 }]
  }
}
```

## Step 3: Make your first authenticated request

Read some products back to prove the whole chain works.

<Tabs items={['Request', 'Response']}>
  <Tab value="Request">
    ```bash
    curl --request GET \
      --url 'https://pim.plytix.com/api/v3/products?_page_size=1' \
      --header 'Authorization: Bearer <access_token>' \
      --header 'Accept: application/json'
    ```
  </Tab>
  <Tab value="Response">
    ```json
    {
      "data": [
        {
          "id": "6a38f614c3d65a5f868b1a06",
          "sku": "BAG-10157",
          "label": "Plytix Backpack",
          "gtin": "9780201379624",
          "status": "Completed",
          "attributes": {
            "brand": "Plytix",
            "color": ["Black"],
            "price": 29.99,
            "short_description": "A sleek, functional backpack designed for everyday use."
          },
          "thumbnail_id": "6a38f5e1c3d65a5f868b18a5",
          "num_variations": 0,
          "product_level": 0,
          "product_family_id": "6a38f5d8c3d65a5f868b186e",
          "overwritten_attributes": [],
          "created": "2026-06-22T08:45:08.648000",
          "modified": "2026-09-14T11:02:47.113000"
        }
      ],
      "errors": [],
      "pagination": {
        "next_page": "http://pim.plytix.com/api/v3/products?_page_size=1&_page=2"
      }
    }
    ```
  </Tab>
</Tabs>

A `200` here confirms the whole setup: your credentials were valid, the token exchange worked, and your headers are right. A `401` with `{"detail": "Unauthorized"}` means the token is missing, malformed, or expired, so go back to step 2.

Three things in that response are worth noticing now, because they shape every integration you build on top of it:

- **Every response is an envelope.** `data`, `errors`, and `pagination` are always there. Your own values live in `attributes`, keyed by attribute name, while fields like `sku` and `status` sit at the top level.
- **`next_page` is a complete URL, and it uses `http`.** That address redirects to `https`, and many HTTP clients drop the `Authorization` header across a scheme change, which turns page two into a surprise `401`. Rewrite the scheme to `https` before you request it.
- **There's no total count.** Page until `next_page` stops appearing; on the last page the key is absent rather than `null`.

<Callout type="idea" title="Drop the page size once you're done testing">
  `_page_size=1` keeps this example readable. The default is 25 and the maximum is 1000, so raise it for real work.
</Callout>
