This tutorial takes you from an empty terminal to a real response from your own catalog. You'll create an access token in your Plytix account settings and use it to read products out of your account. It's written for anyone starting an integration, whether you're syncing an ERP, building an export, or sizing up what the API returns before you plan anything.

**Learning objectives:** By the end of this tutorial, you will be able to:

- Create a V3 access token with the permissions your integration needs
- Make an authenticated request and read the search response Plytix returns

## Before you begin

Make sure you have the following:

- **V3 beta access for your account.** The V3 API is in beta. If the **API v3** tab doesn't appear in your account settings, contact your account manager to request access.
- **A Plytix user with access to products.** A token can never grant more access than your user role allows, so your role needs to let you read products.
- **A terminal with `curl`** or any HTTP client you prefer. Every example here is a `curl` command you can paste and run.

## Step 1: Create an access token

An access token identifies your integration to the V3 API. You create it once in your account settings, and send it with every request until it expires.

1. **Open** your account settings and select the **API v3** tab.
2. **Select** **Create access token**.
3. **Enter** a name, such as `Quickstart`.
4. **Choose** an expiration date. 7 days is enough for this tutorial.
5. **Choose** **Read-only** permissions. This tutorial only reads data.
6. **Select** **Create token**.
7. **Copy** the token and store it somewhere safe, then confirm that you've saved it.

<Callout type="warn" title="You can copy the token only once">
  Plytix shows the token's value only when you create it. If you lose it, rotate the token from the **API v3** tab to get a new value. See [Authentication](/reference/v3/authentication) for rotation, revocation, and the other permission options.
</Callout>

There's no token request to make: the value you copied is the bearer token you send. Every request needs it in an `Authorization: Bearer <access_token>` header.

## Step 2: Make your first authenticated request

Read some products back to prove the whole chain works.

<Tabs items={['Request', 'Response']}>
  <Tab value="Request">
    ```bash
    curl --request GET \
      --url 'https://pim.plytix.com/api/v3/products?_page_size=1' \
      --header 'Authorization: Bearer <access_token>' \
      --header 'Accept: application/json'
    ```
  </Tab>
  <Tab value="Response">
    ```json
    {
      "data": [
        {
          "id": "6a38f614c3d65a5f868b1a06",
          "sku": "1001",
          "label": "Black Wavy Frost Glass Vessel Bowl",
          "gtin": "3234567890126",
          "status": "Completed",
          "attributes": {
            "brand": "Plytix",
            "color": "Glass",
            "suggested_retail_price": 310.24,
            "feature_description": "Fully tempered glass that withstands high temperatures."
          },
          "thumbnail_id": "6a38f5e1c3d65a5f868b18a5",
          "product_level": 0,
          "product_family_id": "6a38f5d8c3d65a5f868b186e",
          "created": "2026-06-22T08:45:08.648000",
          "modified": "2026-09-14T11:02:47.113000"
        }
      ],
      "errors": [],
      "pagination": {
        "next_page": "http://pim.plytix.com/api/v3/products?_page_size=1&_page=2"
      }
    }
    ```
  </Tab>
</Tabs>

The sample response is trimmed for readability. A `200` here confirms the whole setup: your token is valid, it can read products, and your headers are right. A `401` with `{"detail": "Unauthorized"}` means the token is missing, copied incompletely, or no longer valid, so check it against step 1. A `403` means the token authenticated but lacks the permission the request needs.

Three details in that response are worth noticing now, because they shape every integration you build on top of it:

- **A search response carries `data`, `errors`, and `pagination`.** Other operations return different bodies, and a `204` has none, so check each operation's documented response. Your own values live in `attributes`, keyed by attribute label, while fields like `sku` and `status` sit at the top level.
- **`next_page` is a complete URL, and it uses `http`.** That address redirects to `https`, and many HTTP clients drop the `Authorization` header across a scheme change, which turns page two into a surprise `401`. Rewrite the scheme to `https`, and check that the host and path match your original search before you send your token to it.
- **There's no total count.** Page until `next_page` stops appearing; on the last page the key is absent rather than `null`.

<Callout type="idea" title="Increase the page size for production workloads">
  `_page_size=1` keeps this example readable. The default is 25 and the maximum is 1000.
</Callout>
