This guide describes how authorizing an AI assistant to act on your Plytix account is expected to work: choosing the credential and the role behind it, connecting your client, confirming the connection works, and revoking it when you're done. It assumes the Platform MCP reuses Plytix's existing API Key credential, which is unconfirmed. Access is controlled by roles, so read [Permissions and security considerations](/docs/guides/platform-mcp/permissions-and-security) first. Use a test account while you follow it, because an agent with write access changes your catalog when it acts.

## Prerequisites

Make sure you have the following:

- **A Plytix account with API access.** Only Owners and Admins can create and manage API credentials. If you don't have Admin rights, ask an account Owner or Admin to complete the credential step, or to grant you those rights.
- **An MCP-compatible client.** See [Supported clients](/docs/guides/platform-mcp/supported-clients) for which assistants and frameworks work, and what each one needs.
- **A decision about access.** Read-only covers auditing, exporting, and answering questions about your catalog. Grant write access only if the agent needs to change data. See [Permissions and security considerations](/docs/guides/platform-mcp/permissions-and-security).

<Callout type="warn" title="Start on a test account">
  An agent with write access changes your catalog when it acts, and Plytix can't undo some changes, such as deletions. Run this setup against a test account first, and connect production only once you've seen the agent behave the way you expect.
</Callout>

## Authorize your client

1. **Decide which role the agent acts under.**

   Plytix grants access by role, not by user, and the same model covers API Keys: an API Key's role determines what it can reach. Create a dedicated team role for the agent rather than reusing an Owner or Admin role. Team roles are a paid feature. If your plan doesn't include them, the four system roles are the only option, and all of them except Blocked can edit every PIM section. Start with View across every area, then turn on Edit only where the agent's work needs it.

   {/* FLAG: Role model unconfirmed (open):
     It's not yet confirmed whether the Platform MCP acts as the authorizing user, inheriting that person's role, or as a separate credential with its own role the way API Keys work today. If it acts as the user, a dedicated role means creating a dedicated user, which is a different instruction than the one above.
   */}

2. **Create the credential in Plytix.**

   If the Platform MCP reuses the existing credential, that means an API Key. This is unconfirmed.

   1. **Sign in** at [accounts.plytix.com](https://accounts.plytix.com).
   2. **Open** the **API** tab.
   3. **Click** **Create API Key**.
   4. **Give** the API Key a name and set its role. Name it after the assistant or the person using it, so you can tell later who had access.
   5. **Copy** the **API Key** with the clipboard icon, and reveal the **API password** with the eye icon.

   You can edit, re-role, or delete an API Key later from the same tab.

   <Callout type="warn" title="Changing an API Key's role can break what's using it">
     Plytix warns that changing an existing API Key's role can stop an integration working. Create a new API Key for the agent rather than re-roling one that something else already depends on.
   </Callout>

3. **Add the server to your client.**

4. **Complete the authorization.**

5. **Verify with a read-only question.**

   Ask the assistant something that needs real data and that you can check yourself:

   ```text
   Using Plytix, how many products are in my account, and what are the five
   most recently updated ones?
   ```

   Compare the answer against Plytix. A correct count means the connection works and the role can read. An answer with no specifics usually means the assistant didn't call Plytix at all, so name the source in your prompt and ask again.

6. **Confirm the write boundary, if you granted one.**

   Ask the agent to make one small, reversible change on a test record, then check it in Plytix. Confirming write access on a record you chose is better than discovering it partway through a batch.

## Revoke access

Remove access when the agent no longer needs it, or when you're done testing. Follow these steps to revoke it:

1. **Remove the server from your client**, so it stops trying to connect.
2. **Delete or re-role the credential in Plytix**, from the same **API** tab where you created it. Removing the server from a client doesn't delete the API Key in Plytix, so revoke it on the Plytix side too.

## Troubleshooting

Check the problems below if you run into issues while authorizing a client.

<Accordions type="multiple">
  <Accordion title="The assistant reports being connected but every request fails" value="connected-all-fail">
    Check the credential first and the role second. The two fail at different points, and the status code tells you which. A `401` means the credential wasn't accepted, so the API Key, the password, or the way your client stores them is wrong. A `403` means the credential was fine but its role isn't allowed to do what the agent asked. Verify with a read-only question before you grant write access, so the two cases don't arrive together.
  </Accordion>
  <Accordion title="A long-running job stops partway through with an authorization error" value="long-job-auth-expiry">
    Bearer tokens from the V3 auth flow last 15 minutes. How the Platform MCP handles tokens is not yet confirmed. If a job stops partway through, ask the agent what it finished before you retry, and rerun only the remainder so you don't duplicate work. For large batches, run them as code with its own token handling, as in [Bulk operations for large catalogs](/docs/guides/bulk-operations-for-large-catalogs).
  </Accordion>
  <Accordion title="The agent can read your catalog but can't change anything" value="read-but-not-write">
    That's a role boundary doing its job, not a bug. Check the role's permissions for the specific area the agent was working in, whether that's products, attributes, categories, or assets, since they're set independently of each other. Deciding read-only or read-write before you create the credential saves discovering the limit partway through a task.
  </Accordion>
  <Accordion title="An attribute stays unchanged even though the role has Edit rights on it" value="attribute-permission-import-gap">
    Check whether the change went through an import rather than a direct edit. Attribute-level permissions apply in the Plytix interface but not in the importer, so the same role can be blocked on one path and allowed on the other. Setting Import to View or None on that role closes the gap; see [Permissions and security considerations](/docs/guides/platform-mcp/permissions-and-security).
  </Accordion>
</Accordions>
