This guide walks through authorizing an AI assistant to act on your Plytix account: choosing the credential and the role behind it, connecting your client, confirming the connection works, and revoking it when you're done.

## Prerequisites

Before you start, you need:

- **A Plytix account with API access.** Only Owners and Admins can create and manage API credentials. If you don't have Admin rights, ask an account Owner or Admin to complete the credential step, or to grant you those rights.
- **An MCP-compatible client.** See [Supported clients](/docs/guides/platform-mcp/supported-clients) for which assistants and frameworks work, and what each one needs.
- **A decision about access.** Read-only covers auditing, exporting, and answering questions about your catalog. Grant write access only if the agent needs to change data. See [Permissions and security considerations](/docs/guides/platform-mcp/permissions-and-security).

<Callout type="warn" title="Start on a test account">
  An agent with write access changes your catalog the moment it acts, and Plytix has no undo for those changes. Run this setup against a test account first, and connect production only once you've seen the agent behave the way you expect.
</Callout>

## Authorize your client

1. **Decide which role the agent acts under.**

   Plytix grants access by role, not by user, and the same model covers API keys: a key's role determines what it can reach. Create a dedicated team role for the agent rather than reusing an Owner or Admin role. Start with View across every area, then turn on Edit only where the agent's work needs it.

   {/* FLAG (open):
     `[PENDING]` It's unconfirmed whether the Platform MCP acts as the authorizing user, inheriting that person's role, or as a separate credential with its own role the way API keys work today. If it acts as the user, a dedicated role means creating a dedicated user, which is a different instruction than the one above.
   */}

2. **Create the credential in Plytix.**

   Today, that means an API key:

   1. Sign in at [accounts.plytix.com](https://accounts.plytix.com).
   2. Open the **API** tab.
   3. Click **Create API Key**.
   4. Give the key a name and set its role. Name it after the assistant or the person using it, so you can tell later who had access.
   5. Copy the **API key** with the clipboard icon, and reveal the **API password** with the eye icon.

   You can edit, re-role, or delete a key later from the same tab.

   <Callout type="warn" title="Changing a key's role can break what's using it">
     Plytix warns that changing an existing API key's role can stop an integration working. Create a new key for the agent rather than re-roling one that something else already depends on.
   </Callout>

3. **Add the server to your client.**

   Register the Platform MCP endpoint under a server name. The exact syntax depends on your client, and [Supported clients](/docs/guides/platform-mcp/supported-clients) covers the per-client format.

4. **Complete the authorization.**

   {/* FLAG (open):
     **Insufficient source:** this step can't be written until the conflict at the top of this page is resolved. 5. **Verify with a read-only question.**

   Ask the assistant something that needs real data and that you can check yourself:

   ```text
   Using Plytix, how many products are in my account, and what are the five
   most recently updated ones?
   ```

   Compare the answer against Plytix. A correct count means the connection works and the role can read. An answer with no specifics usually means the assistant didn't call Plytix at all, so name the source in your prompt and ask again.

6. **Confirm the write boundary, if you granted one.**

   Ask the agent to make one small, reversible change on a test record, then check it in Plytix. Confirming write access on a record you chose is better than discovering it partway through a batch.

## Revoke access

Remove access when the agent no longer needs it, or when you're done testing. Two steps, and the second is the one people skip:

1. **Remove the server from your client**, so it stops trying to connect.
2. **Delete or re-role the credential in Plytix**, from the same **API** tab where you created it. Removing the server from a client doesn't invalidate the credential, so a copy of it elsewhere still works until you revoke it on the Plytix side.

## Troubleshooting

Check the problems below if you run into issues while authorizing a client.

<Accordions type="multiple">
  <Accordion title="The assistant reports being connected but every request fails" value="connected-all-fail">
    Check the credential first and the role second, because the two fail at different points and the status code tells you which you're looking at. A `401` means the credential itself wasn't accepted, so the key, the password, or the way your client stores them is wrong. A `403` means the credential was fine but its role isn't allowed to do what the agent asked. Verifying with a read-only question before you grant write access keeps these two cases from arriving at the same time.
  </Accordion>
  <Accordion title="A long-running job stops partway through with an authorization error" value="long-job-auth-expiry">
    Bearer tokens from the current Plytix auth flow last 15 minutes, which is short enough that an agent working through a large batch can outlive its own token. Reconnect, ask the agent what it finished before you retry, and rerun only the remainder so you don't duplicate work. The durable fix is to keep agent-driven jobs short and run large batches as code with its own token handling, as in [Bulk operations for large catalogs](/docs/guides/bulk-operations-for-large-catalogs).
  </Accordion>
  <Accordion title="The agent can read your catalog but can't change anything" value="read-but-not-write">
    That's a role boundary doing its job, not a bug. Check the role's permissions for the specific area the agent was working in, whether that's products, attributes, categories, or assets, since they're set independently of each other. Deciding read-only or read-write before you create the credential saves discovering the limit partway through a task.
  </Accordion>
  <Accordion title="An attribute stays unchanged even though the role has Edit rights on it" value="attribute-permission-import-gap">
    Check whether the change went through an import rather than a direct edit. Attribute-level permissions apply in the Plytix interface but not in the importer, so the same role can be blocked on one path and allowed on the other. Setting Import to View or None on that role closes the gap; see [Permissions and security considerations](/docs/guides/platform-mcp/permissions-and-security).
  </Accordion>
</Accordions>
