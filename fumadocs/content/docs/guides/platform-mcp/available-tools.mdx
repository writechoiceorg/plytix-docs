This page documents the PIM V3 API resources an agent could work with through the Platform MCP, which operations each one supports, and which are read-only.

Key points on this page:

- The Plytix PIM V3 API spans products, assets, and outputs.
- Most groups support read and write. Some are read-only, and one has no update operation.
- Access to any of them is expected to be bounded by a role, though this is not yet confirmed for the Platform MCP.
- Search operations are where filtering and pagination happen.

## How resources map to tools

The Platform MCP is expected to sit on top of the PIM V3 API, so the resources below are the surface an agent would work with. This mapping is not yet confirmed.

Each group follows the same shape in V3. A search operation returns a filtered, paged collection. A get operation returns one record by identifier. Create, update, and delete operate on single records. There are no bulk write operations in V3, which is why a large batch runs as many single calls and needs pacing. See [Bulk operations for large catalogs](/docs/guides/bulk-operations-for-large-catalogs).

## Product data

Plytix PIM product data.

| Resource | Read | Write | Covers |
|---|---|---|---|
| Products | Search, get | Create, update, delete | Product records and their attribute values |
| Product attributes | Search, get | Create, update, delete | Attribute definitions available to products |
| Product attribute groups | Search, get | Create, delete | Groupings of attributes. No update operation in the `openapi_pimv3.json` spec. The latest spec (2026-10-02) adds one, so the current spec is not yet confirmed |
| Product categories | Search, get | Create, update, delete | The category tree and its entries |
| Product families | Search, get | Create, update, delete | Family records. Update renames the family only |
| Family attributes | Search, get | Create, update, delete | Which attributes belong to a given family. Searching uses `/family-attributes`. Writes use `/product-families/{id}/attributes` |
| Product family models | Search, get | None | Family model definitions. Read-only. Not in the latest spec (2026-10-02), so the current spec is not yet confirmed |
| Relationships | Search, get | Create, update, delete | Relationship type definitions |
| Product relationships | Search, get | Create, update, delete | Relationships attached to a specific product. Searching uses `/product-relationships`. Writes use `/products/{id}/relationships` |
| Related products | Search, get | None | The products on the far side of a relationship. Read-only |
| Product lists | Search, get | Create, update, delete | Product lists as exposed by the `pim-product-lists` resource. Not yet confirmed to match Smart Lists, which are UI-only |

<Callout type="info" title="Two of these are read-only">
  Product family models and related products expose no create, update, or delete operations in V3. An agent can read them to understand your structure, and it changes that structure through product families and product relationships instead.
</Callout>

## Assets

Digital assets and the ways they're organized.

| Resource | Read | Write | Covers |
|---|---|---|---|
| Assets | Search, get | Create, update, delete | Asset records and their metadata |
| Asset categories | Search, get | Create, update, delete | The asset category tree |
| Asset lists | Search, get | Create, update, delete | Saved asset lists |

## Outputs, imports, and connections

These groups exist in the V3 spec. Their MCP behavior is not yet confirmed.

| Resource | Read | Write | Covers |
|---|---|---|---|
| Connections | Search, get | Create, update, delete | Dropbox and FTP connections |
| Import profiles | Search, get | Create, update, delete | Import profile definitions |
| Brand Portals (`ecatalogs`) | Search, get | Create, update, delete | Brand Portal catalogs |
| PDF catalogs | Search, get | Create, update, delete | Product Data Sheet catalogs |

## Searching and paging

Search operations are what an agent calls most, because nearly every request starts with finding the right records. Two behaviors show up as wrong answers rather than errors:

- **Results are paged.** An agent that stops at the first page reports a count lower than the truth.
- **Filters support more than equality.** Plytix supports OR logic and completeness filters, which is what makes questions like "which products are missing a description or an image" answerable in one pass. See [Audit product data quality with filters](/docs/guides/auditing-product-data-quality-with-filters).

For the full parameter list on any of these operations, see the [V3 API reference](/docs/reference/v3).

## What has no tool

A tool is not expected to exist for something the API doesn't expose. Two gaps are worth stating directly:

- **Account administration**, including users, roles, and API keys, is an Owner and Admin task in the Plytix interface.
- **Channel configuration** is set up in the Plytix interface. Whether channels can also be managed through the API is not yet confirmed. Destinations is not yet fully live.

Reaching a resource also isn't the same as being allowed to change it. A role is expected to decide that, which is not yet confirmed for the Platform MCP. See [Permissions and security considerations](/docs/guides/platform-mcp/permissions-and-security).
