This page documents the access boundaries that are expected to apply to an AI agent connected to the Plytix Platform MCP, and the practices worth adopting before you grant one write access.

Key points on this page:

- A user's or an API Key's reach is bounded by a Plytix role. Whether an agent's reach is bounded the same way is not yet confirmed.
- Plytix has four system roles and supports up to 15 custom team roles with per-area permissions.
- Attribute-level permissions don't apply to imports, which is the one gap worth checking before you trust a restricted role.
- Plytix can't undo some changes, such as deletions, so read and write belong in separate steps.
- Product data an agent reads can carry instructions the agent acts on. Treat supplier-supplied text as untrusted.

## Access boundaries

Plytix limits access by role, not by user. You assign permissions to a role, then assign that role to a person or an API key. If the Platform MCP follows the same pattern, the agent's reach would be whatever its role allows.

### System roles

Every Plytix account has four system roles. All of them except Blocked can view and edit every PIM section, so they're a coarse control, not a precise one.

| Role | PIM access | Account administration | Notes |
|---|---|---|---|
| Owner | View and edit all sections | View and edit all sections | Can delete the account and transfer ownership |
| Admin | View and edit all sections | View and edit all sections | Can create and manage API keys |
| User | View and edit all sections | Account Summary only | No access to the rest of account administration |
| Blocked | None | Account Summary only | Cannot access the Plytix PIM at all |

A user or API Key under a system role other than Blocked can edit everything in the Plytix PIM. To narrow that, you need a custom team role. Whether an agent connected through the Platform MCP follows this is not yet confirmed.

### Team roles

Team roles are a paid feature that lets an administrator build custom permission sets. An account supports up to 15 custom roles. Each area is set to Edit, View, or in some cases None.

| Permission type | What it allows |
|---|---|
| Edit | Add and delete information |
| View | Read information, and for products, export and filter it |
| None | No visibility into the area at all |

These are the Plytix PIM areas you can set:

| Area | Options | Covers |
|---|---|---|
| Products | Edit, View | All product management and product lists |
| Attributes (product level) | Edit, View | Whether attribute values can be changed or only read |
| Families (product level) | Edit, View | The families and variants tab |
| Categories (product level) | Edit, View | Assigning products to categories, and changing those assignments |
| Relationships (product level) | Edit, View | Adding and removing product relationships |
| Import | Edit, View, None | Imports, feeds, profiles, and logs |
| Settings Management | Edit, None | The Settings tab under Automations |
| Assets | Edit, View | Asset and asset list management |
| Asset categories | Edit, None | Asset category settings |
| Connections | Edit, None | Dropbox and FTP connections |
| Automations | Edit, View, None | Condition-based automated actions |
| Brand Portals, Channels, Product Data Sheets | Edit, View, None | Add-on settings, shown only for add-ons active on your account |

### Attribute-level permissions

Beyond the area level, an administrator can set View or Edit per individual attribute, per custom role. This is how you lock a price or a compliance field while still letting a role edit descriptions.

<Callout type="warn" title="Attribute permissions don't cover imports">
  Attribute-level permissions limit editing in the Plytix interface, but not in the importer. A role with View rights on an attribute and Edit rights on Import can still change that attribute through an import. To close the gap, set Import to View or None on that role.

  Confirm how the Platform MCP writes data before relying on attribute-level permissions to protect a field. This is not yet confirmed.
</Callout>

### What sits outside the API

Some parts of Plytix are configured in the Plytix interface.

- **Channels**, including Shopify, BigCommerce, and feed exports, are set up in the Plytix interface. Whether channels can also be managed through the API is not yet confirmed. Destinations is not yet fully live.
- **Account administration**, including creating users, roles, and API keys, is an Owner and Admin task in the interface.

## Security practices

These practices are general guidance, not confirmed Plytix Platform MCP behavior. The sections below cover:

- Grant the narrowest role that completes the job
- Keep read and write in separate steps
- Treat product data as untrusted input
- Protect the connection itself
- Watch the pace

### Grant the narrowest role that completes the job

Create a dedicated team role for the agent rather than connecting it under an Owner or Admin account. Start with View across the board, then turn on Edit only for the areas the agent's actual work needs. A read-only agent covers auditing, exporting, and answering questions about the catalog, which is most of what people ask an agent to do.

### Keep read and write in separate steps

Plytix can't undo some changes, such as deletions. Ask for a plan, review it, then approve the change as a second prompt. This is the discipline every workflow in [Practical examples](/docs/guides/platform-mcp/practical-examples) follows.

### Treat product data as untrusted input

An agent reading your catalog is reading text that came from suppliers, importers, and integrations. If that text contains something shaped like an instruction, an agent may act on it. This is general guidance, not from Plytix sources. It is a risk for any agent that reads data and can also write it, not a Plytix-specific flaw, and the practical defense is the same one as above: don't let a single prompt both read unfamiliar data and write changes.

### Protect the connection itself

If your client stores an authorization token or API Key, that storage is worth a look before you connect an account with write access.

- Check whether your client writes its configuration into a file that gets committed to a repository or synced across machines.
- Disconnect the server when you stop using it, and revoke the credential on the Plytix side rather than only removing it from the client. How revocation works for the Platform MCP is not yet confirmed.
- Name the connection after the person or tool using it, following the same practice Plytix recommends for API keys, so you can tell later who had access.

### Watch the pace

In the V3 API, rate limits vary by account and are carried in your access token's claims. An agent working through a large batch one item at a time can reach the limit and fail partway through, which leaves a job half done rather than cleanly failed. For large batches, see [Bulk operations for large catalogs](/docs/guides/bulk-operations-for-large-catalogs).

## What the Process Log records

Plytix records processing events in the Process Log, reachable from the icon next to your account name. The **Activity** section lists the last 25 completed events, each with an action, the user who ran it, and a timestamp. Imports, exports, feed and channel processing, bulk updates, and post-calculated attribute edits all appear there.

Individual record writes made through the API are not confirmed to appear in the Process Log.
