import { ArrowClockwiseRegular, DocumentEditRegular } from '@/components/icons';

Remove one category from a product, or remove a product's link to one relationship type, without touching the product's other links. Each is a link between two entities, and Plytix V3 gives you a dedicated endpoint to add or remove it: `POST` to the collection to link, `DELETE` on the specific link to unlink. Removing a relationship link removes every related product the product has under that relationship type, so it isn't a way to remove a single related product. The relationship type and the products themselves stay. This guide covers categories and relationships, and explains how a product's thumbnail and other assets are set. All requests use the V3 API with a bearer token. A successful `PATCH` or `DELETE` returns `204` with an empty body, which confirms the change. Read the product back when you need to inspect the result.

## Prerequisites

Before you start, make sure you have the following:

- A V3 access token with the permissions this guide needs. See [Authentication](/reference/v3/authentication), or the [Quickstart](/docs/guides/quickstart) for a first walkthrough.
- The product's ID, and the ID of the category or relationship you want to remove.

## Remove a category from a product

Follow the steps below to read a product's current categories, remove one of them, and check the result.

1. **Read the product's current categories.**

   ```bash
   curl "https://pim.plytix.com/api/v3/products/<product_id>/categories" \
     -H "Authorization: Bearer <access_token>"
   ```

   The response lists each linked category in full, including its `id` and `name`. You need the `id` of the one you're removing.

   You can also get the same data from the search endpoint with `_fields=categories`, which is useful when you're looking up several products at once. What you can't do is ask for `category_ids`: Plytix hides the ID arrays behind a product's links, such as `category_ids` and `asset_ids`, and returns `400` if you request one.

2. **Unlink the category.**

   ```bash
   curl -X DELETE "https://pim.plytix.com/api/v3/products/<product_id>/categories/<category_id>" \
     -H "Authorization: Bearer <access_token>"
   ```

   This removes only the category you name. The product keeps its other categories and its other data. A successful unlink returns `204` with an empty body.

   <Callout type="warn" title="Unlink the category, don't delete it">
     `DELETE /api/v3/product-categories/<category_id>` deletes the category itself, not one product's link to it. In Plytix's controlled Dev test (October 2026), deleting a parent category also deleted its child and grandchild categories, and the test product lost its associations with them. The product itself stayed. The effect on many products, and on production, hasn't been tested yet.
   </Callout>

3. **Link a category, if you're moving a product rather than only removing it.**

   ```bash
   curl -X POST "https://pim.plytix.com/api/v3/products/<product_id>/categories" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"id": "<category_id>"}'
   ```

   The body is an object with a single `id` key, not an array and not a `category_ids` wrapper. A successful link returns `201` with the linked category's ID: `{"data": {"id": "<category_id>"}, "errors": []}`. Linking a category that's already linked returns `409`, described in [Troubleshooting](#troubleshooting).

4. **Check the result, if your integration needs it.**

   ```bash
   curl "https://pim.plytix.com/api/v3/products/<product_id>/categories" \
     -H "Authorization: Bearer <access_token>"
   ```

   The `204` already confirms the unlink. Read the categories back when your integration needs to inspect the resulting state.

## Remove a relationship from a product

{/* FLAG (open): REL-23. The 2026-10-19 spec removes `product_relationships` and the `/api/v3/products/{product_id}/relationships` routes in favor of `product_relationships_from`/`_to` and `/api/v3/products/{product_identifier}/product_relationship_types`. Rewrite this section once Plytix classifies the new operations. */}

Relationships work the same way as categories, with one extra layer: the relationship type is an account-level entity, and the link between two products lives under it.

Follow the steps below to remove a relationship link without deleting the relationship type or either product.

1. **Read the product's current relationships.**

   ```bash
   curl -G "https://pim.plytix.com/api/v3/products" \
     -H "Authorization: Bearer <access_token>" \
     --data-urlencode "sku=<sku>" \
     --data-urlencode "_fields=product_relationships"
   ```

   Each entry carries a `relationship_id`, which is what you need next.

2. **Unlink the relationship.**

   ```bash
   curl -X DELETE "https://pim.plytix.com/api/v3/products/<product_id>/relationships/<relationship_id>" \
     -H "Authorization: Bearer <access_token>"
   ```

   This removes the product's link to that relationship type, including every related product listed under it for this product. You can't use it to remove one related product. It returns `204`. The relationship type itself survives, and so does every product that was on the other end of the link.

3. **Check the result, if your integration needs it.**

   Repeat the read from step 1. The entry for that `relationship_id` should be gone.

<Callout type="warn" title="Deleting the relationship type is a different action">
  `DELETE /relationships/{relationship_id}` deletes the relationship type from your whole account. Check what uses it before you call it. Use the product-scoped path above when you only mean to unlink one product.
</Callout>

## Change or clear a product's thumbnail

A product's thumbnail is set through `thumbnail_id` on the product itself, not through a link endpoint. Follow the steps below to change or clear a thumbnail.

1. **Point the thumbnail at a different asset.**

   ```bash
   curl -X PATCH "https://pim.plytix.com/api/v3/products/<product_id>" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"thumbnail_id": "<new_asset_id>"}'
   ```

2. **Clear it entirely by sending `null`.**

   ```bash
   curl -X PATCH "https://pim.plytix.com/api/v3/products/<product_id>" \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"thumbnail_id": null}'
   ```

   Both return `204`. Clearing the thumbnail changes only the product's reference to the asset. The asset itself stays in Plytix DAM; deleting it is a separate action, `DELETE /api/v3/assets/<asset_id>`, which removes it from your account. In testing, a product whose only asset was its thumbnail also showed an empty `assets` list once the thumbnail was cleared. An asset that a media attribute still references stays in `assets` after you clear the thumbnail.

## Connect other assets to a product

There's no link or unlink endpoint for assets: `POST /products/<product_id>/assets` returns `405`. You connect other assets through media and media gallery attributes, which hold assets as values in the product's `attributes` map. Each takes asset IDs in its own shape:

- A media attribute takes one bare asset ID, such as `"<asset_id>"`.
- A media gallery attribute takes an array of asset IDs, such as `["<asset_id_1>", "<asset_id_2>"]`.
- Objects such as `{"id": "<asset_id>"}` are rejected, and so is the other attribute's shape, an array on a media attribute or a bare string on a gallery.

These formats were tested on the attribute's own path, in a `PATCH` of the whole `attributes` map, and when creating a product. This request sets a gallery:

```bash
curl -X PATCH "https://pim.plytix.com/api/v3/products/<product_id>/attributes/<gallery_label>" \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '["<asset_id_1>", "<asset_id_2>"]'
```

Keep these behaviors in mind when you read the result back:

- Reads return expanded asset objects, not the IDs you wrote, so compare them by each object's `id`.
- A gallery keeps the order you send and drops duplicate IDs. That order belongs to the gallery: the product's `assets` list can come back in a different order.
- Gallery order doesn't choose the thumbnail. Set the main image with `thumbnail_id`, as shown in [Change or clear a product's thumbnail](#change-or-clear-a-products-thumbnail).

To disconnect assets, send `[]` to a gallery, or use `DELETE /products/<product_id>/attributes/<label>` on either attribute. A media attribute rejects `""`. Clearing or unlinking removes only the product's association: the asset stays in Plytix DAM, and deleting it is the separate `DELETE /api/v3/assets/<asset_id>`.

## Troubleshooting

Check the problems below if you run into issues while following this guide.

<Accordions type="multiple">
  <Accordion title={<><code>PATCH /products/&lt;id&gt;</code> returns 422 on <code>category_ids</code></>} value="patch-category-ids-422">
    If the response says `"category_ids: Extra inputs are not permitted"`, you're using the older array-based approach. Plytix now rejects these array fields, and the same applies to the product's other `*_ids` link arrays. Switch to `POST /products/{id}/categories` and `DELETE /products/{id}/categories/{category_id}`.
  </Accordion>
  <Accordion title={<><code>DELETE /products/&lt;id&gt;/categories</code> returns 405</>} value="delete-categories-405">
    The unlink endpoint needs to know which link to remove, so the category ID is part of the path, not optional. The error message spells out the shape it wants: `DELETE /products/{id}/categories/{linked_id}`. Add the category ID and the request succeeds.
  </Accordion>
  <Accordion title={<><code>DELETE /products/&lt;id&gt;/categories/&lt;category_id&gt;</code> returns 404</>} value="delete-category-link-404">
    If the description says the category is not linked to that product through `categories`, the link is already gone, so a repeated unlink can treat it as done. Any other `404` means the request didn't reach a linked pair, for example because the product ID is wrong: check the product with `GET /products/<product_id>` before retrying.
  </Accordion>
  <Accordion title={<><code>POST /products/&lt;id&gt;/categories</code> returns 409</>} value="post-categories-409">
    If the response is `409` with `AlreadyExists` and a description like `"'<category_id>' is already linked to products <product_id> through 'categories'"`, that category is already linked to that product. When your code makes links idempotent, treat the `409` as success only if the IDs in the description match the category and product you sent, or a read of the product's categories shows the link. Handle any other `409` as an error.
  </Accordion>
  <Accordion title={<><code>_fields=category_ids</code> returns 400</>} value="fields-category-ids-400">
    Plytix hides the ID arrays behind a product's links, such as `category_ids` and `asset_ids`, to avoid exposing its internal structure, so this returns a `HiddenFieldError`. Ask for the expanded plural form instead: `_fields=categories` returns the full category objects, which include the IDs you were after.
  </Accordion>
  <Accordion title="A write returned 204 and you can't tell whether it worked" value="write-204-empty">
    Every successful `PATCH` and `DELETE` in V3 returns `204` with an empty body. That status confirms the write succeeded. If your integration needs to inspect the resulting state, read it back with a `GET`.
  </Accordion>
</Accordions>
